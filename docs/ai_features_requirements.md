### 项目上下文（Project Context）

项目上下文是所有 AI 功能的"记忆层"。每次 AI 需求分析不仅提取需求条目，还会从文档中提取更广泛的**项目重要内容**——包括业务规则、架构决策、数据模型、API 契约、术语定义等。这些信息被持久化存储，构成对项目整体认知的上下文知识库。

当后续上传新需求文档时，AI 会自动检索项目上下文中与本次需求相关的**历史模块信息**，从而理解"新增需求与哪些已有模块有交集"、"是否涉及现有功能的变更"、"历史类似需求是如何处理的"。

#### 上下文数据结构

```sql
-- 项目上下文主表：存储从文档中提取的所有重要内容片段
CREATE TABLE project_contexts (
    id SERIAL PRIMARY KEY,
    project_id INT NOT NULL REFERENCES projects(id),
    module_id INT REFERENCES modules(id),          -- 关联的模块（可为空）
    source_type VARCHAR(30) NOT NULL,               -- document / manual / api / analysis
    source_file VARCHAR(255),                       -- 来源文件名
    source_version INT DEFAULT 1,

    -- 核心内容
    context_type VARCHAR(50) NOT NULL,              -- 内容类型（见下方枚举）
    title VARCHAR(255) NOT NULL,                    -- 片段标题
    content TEXT NOT NULL,                           -- 片段内容（纯文本）
    summary TEXT,                                   -- AI 提炼的摘要（用于快速浏览）
    tags JSONB DEFAULT '[]',                        -- 标签
    keywords JSONB DEFAULT '[]',                    -- 关键词（用于匹配检索）

    -- 向量嵌入（用于语义检索）
    embedding vector(1536),                         -- pgvector 向量

    -- 元信息
    importance INT DEFAULT 3,                       -- 重要程度 1-5（AI 自动评估）
    created_at TIMESTAMP DEFAULT NOW(),
    updated_at TIMESTAMP DEFAULT NOW()
);

-- 上下文类型枚举
--   business_rule    - 业务规则 / 业务逻辑
--   data_model       - 数据模型 / 字段定义
--   api_contract     - API 契约 / 接口定义
--   architecture     - 架构决策 / 技术选型
--   term_definition  - 术语定义 / 名词解释
--   requirement      - 功能需求（也写入 requirements 表）
--   constraint       - 约束条件（性能 / 安全 / 合规）
--   user_scenario    - 用户场景 / 用户故事
--   process_flow     - 业务流程 / 状态流转
--   dependency       - 依赖关系（模块间 / 系统间）

CREATE INDEX idx_pc_project ON project_contexts(project_id);
CREATE INDEX idx_pc_module ON project_contexts(module_id);
CREATE INDEX idx_pc_type ON project_contexts(context_type);
CREATE INDEX idx_pc_tags ON project_contexts USING GIN (tags);

-- 存储项目上下文版本快照
CREATE TABLE project_context_snapshots (
    id SERIAL PRIMARY KEY,
    project_id INT NOT NULL REFERENCES projects(id),
    version INT NOT NULL,
    description VARCHAR(255),                       -- 版本说明
    context_ids INT[] NOT NULL,                     -- 该版本包含的 context IDs
    created_at TIMESTAMP DEFAULT NOW()
);

-- 存储语义检索的匹配记录（用于审计和理解 AI 的分析依据）
CREATE TABLE context_matches (
    id SERIAL PRIMARY KEY,
    analysis_id INT NOT NULL,                       -- 关联的分析记录
    context_id INT NOT NULL REFERENCES project_contexts(id),
    similarity_score FLOAT,                          -- 语义相似度
    match_reason VARCHAR(255),                       -- 匹配原因说明
    created_at TIMESTAMP DEFAULT NOW()
);
```

#### 上下文生命周期

```
文档上传
  ↓
文档分块处理（按章节 / 段落拆分）
  ↓
AI 内容提取
  ├─ 识别内容类型（业务规则 / 数据模型 / API / ...）
  ├─ 提炼摘要和关键词
  ├─ 评估重要程度（1-5）
  └─ 生成向量嵌入
  ↓
关联已有上下文
  ├─ 语义检索已有上下文，发现重复或关联
  ├─ 标记"更新了已有上下文"或"新增上下文"
  └─ 记录匹配关系
  ↓
存储到 project_contexts
  ↓
更新上下文快照（版本 +1）
```

#### 上下文在使用时的注入策略

当 AI 功能被调用时，项目上下文不会全部注入（会超出 token 限制），而是采用**按需检索 + 分级注入**策略：

```
用户输入（新需求 / 要分析的文档）
  ↓
步骤 1：关键词提取 → 从用户输入中提取关键术语 / 模块名 / 功能名词
  ↓
步骤 2：混合检索 → 使用关键词匹配 + 向量语义检索，找到最相关的 N 条上下文
  ├─ 检索范围：当前项目下的所有上下文
  ├─ 排序依据：语义相似度 + 关键词命中 + 重要程度
  └─ 返回 Top-K（K 可根据 token 预算动态调整，默认 20）
  ↓
步骤 3：上下文编排 → 将检索到的上下文按以下顺序组装
  ├─ 高优先级：直接命中的模块上下文、业务规则
  ├─ 中优先级：关联模块的上下文、数据模型
  ├─ 低优先级：全局性的架构和术语
  └─ 去重：移除与本次分析无关的冗余信息
  ↓
步骤 4：注入 Prompt → 将编排后的上下文注入 AI 的 Prompt
  └─ 最终 Prompt = 系统指令 + 项目上下文 + 用户输入 + 输出格式要求
```

#### 上下文在跨模块分析中的关键作用

当新需求与历史模块有交集时，项目上下文起到决定性作用：

```
示例场景：
用户上传新 PRD，其中包含"用户在订单详情页可以申请售后"

没有项目上下文时：
  AI 只分析这段文本 → 生成"订单售后申请"的需求条目和相关用例
  但 AI 不知道：平台已有"订单"模块、"售后"模块、"退款"模块
  也看不到这些模块的已有用例和接口定义

有项目上下文时：
  AI 先检索到 → 已有"订单模块"（包含订单详情页的定义）
              → 已有"售后模块"（包含售后申请的处理流程）
              → 已有"退款模块"（与售后关联的退款逻辑）
  AI 的 Prompt 中会包含：
    "该项目已有以下相关模块和上下文：
     1. 订单模块 - 订单详情页包含: 订单状态列表、商品列表、金额展示
     2. 售后模块 - 已有售后类型: 仅退款、退货退款、换货
     3. 退款模块 - 退款规则: 下单24小时内可全额退款"
  AI 分析结果会指出：
    "本次新增的'售后申请'功能与已有'售后模块'和'退款模块'有交集，
     建议复用现有售后类型定义，并在退款规则中增加'售后申请中'的状态"
```

### 模型提供商与路由（Model Providers & Routing）

AI Gateway 通过 LiteLLM 实现统一的模型接入层，支持同时接入多种模型提供商，实现灵活的路由、故障转移和成本优化。

#### 支持的模型提供商

| 类别 | 提供商 | 接入方式 | 典型模型 | 适用场景 |
|------|--------|---------|---------|---------|
| 云端 API | OpenAI | LiteLLM proxy | GPT-4o / GPT-4o-mini | 通用分析、复杂推理 |
| 云端 API | Anthropic | LiteLLM proxy | Claude Sonnet / Haiku | 长文档分析、需求提取 |
| 云端 API | Google | LiteLLM proxy | Gemini Pro / Flash | 多模态、大上下文 |
| 云端 API | 阿里通义 | LiteLLM proxy | Qwen-Max / Qwen-Turbo | 中文优化、成本敏感 |
| 云端 API | 百度文心 | LiteLLM proxy | ERNIE-Bot | 国内合规场景 |
| 云端 API | DeepSeek | LiteLLM proxy | DeepSeek-V3 / R1 | 代码生成、推理 |
| 本地模型 | Ollama | HTTP API | Qwen2.5 / DeepSeek-Coder / LLaMA | 内网部署、数据安全 |
| 本地模型 | vLLM | OpenAI 兼容 API | Qwen2.5 / DeepSeek / Yi | 高性能本地推理 |
| 本地模型 | llama.cpp | HTTP Server | LLaMA / Mistral / Qwen | 资源受限环境 |

#### 模型路由规则

```
用户/功能指定分析模式
  ↓
路由策略决定使用的模型：
  ├─ 按分析模式路由
  │   ├─ 快速扫描 → GPT-4o-mini / Qwen-Turbo / 本地小模型
  │   ├─ 深度分析 → GPT-4o / Claude Sonnet / DeepSeek-V3
  │   ├─ 多模型集成 → 主模型 + 验证模型并行调用
  │   └─ 审查模式 → 与生成时不同的模型（避免偏见）
  ├─ 按成本路由
  │   ├─ 高预算 → 旗舰模型
  │   ├─ 中预算 → 平衡模型
  │   └─ 低预算 → 经济模型或本地模型
  ├─ 按数据安全路由
  │   ├─ 敏感数据 → 仅本地模型
  │   └─ 普通数据 → 云端 API + 本地均可
  └─ Fallback 策略
      ├─ 主模型失败 → 自动切换到备用模型
      ├─ 云端超时 → 降级到本地模型
      └─ 所有模型失败 → 返回错误信息 + 推荐手动处理
```

#### 模型选择对结果的影响

| 因素 | 云端大模型 | 本地模型 |
|------|-----------|---------|
| 推理能力 | 强（参数千亿级） | 中（取决于硬件和模型大小） |
| 上下文窗口 | 大（128K-200K tokens） | 中（8K-128K，受显存限制） |
| 延迟 | 中（网络传输+排队） | 低（本地推理） |
| 数据安全 | 数据出站 | 数据不出内网 |
| 成本 | 按 token 付费 | 仅硬件成本 |
| 中文能力 | 取决于模型（Qwen 系最佳） | 取决于模型 |
| 长文档处理 | 适合（大窗口） | 需分块策略 |

### 分析模式（Analysis Modes）

每个 AI 功能（需求分析、用例生成、用例检查等）都支持多种分析模式。用户可以根据场景选择最合适的模式，在速度、质量、成本之间取得平衡。

#### 分析模式总览

| 模式 | 标识符 | 典型模型级别 | 耗时 | 成本 | 适用场景 |
|------|--------|------------|------|------|---------|
| 快速扫描 | `quick` | 轻量模型 | 快（秒级） | 低 | 日常快速查看、草稿生成、初步筛选 |
| 标准分析 | `standard` | 平衡模型 | 中（分钟级） | 中 | **默认模式**，日常使用 |
| 深度分析 | `deep` | 旗舰模型 | 慢（数分钟） | 高 | 重要模块的全量需求分析、复杂业务逻辑 |
| 多模型集成 | `multi_model` | 多个模型 | 最慢 | 最高 | 关键决策、高风险模块、需要交叉验证 |
| 增量分析 | `incremental` | 任意 | 快 | 低 | 在已有分析基础上补充少量新内容 |
| 审查模式 | `review` | 与生成时不同的模型 | 中 | 中 | 交叉验证已有内容（避免同模型偏见） |

#### 快速扫描模式（Quick Scan）

| 特性 | 说明 |
|------|------|
| 目标 | 在最短时间内给出粗略分析结果，供用户快速了解文档内容 |
| 模型策略 | 使用轻量模型（GPT-4o-mini / Qwen-Turbo / 本地 7B 模型） |
| 上下文策略 | 仅检索高优先级的项目上下文（Top-5），省略低优先级上下文 |
| 输出粒度 | 粗粒度：仅提取主要需求条目和业务规则，不深入分析交叉模块 |
| Prompt 策略 | 使用简化 Prompt，要求模型直接给出结果，无需中间推理 |
| 超时控制 | 设置较短的超时时间（30s），超时直接返回已生成的部分结果 |
| 适用场景 | 快速浏览新文档、初步评估需求范围、非关键模块的分析 |

#### 标准分析模式（Standard）

| 特性 | 说明 |
|------|------|
| 目标 | 平衡速度和质量，作为日常使用的默认模式 |
| 模型策略 | 使用平衡模型（GPT-4o / Claude Sonnet / Qwen-Max） |
| 上下文策略 | 完整的上下文字段检索（Top-20）+ 分级编排 |
| 输出粒度 | 中粒度：提取所有内容类型，包含交叉模块分析 |
| Prompt 策略 | 完整 Prompt 模板，包含详细的输出格式约束 |
| 超时控制 | 合理超时（120s），配合 SSE 流式输出让用户感知进度 |
| 适用场景 | 日常需求分析、功能用例生成、测试计划生成 |

#### 深度分析模式（Deep）

| 特性 | 说明 |
|------|------|
| 目标 | 以最高质量完成分析，不吝啬 token 和推理时间 |
| 模型策略 | 使用旗舰模型（Claude Sonnet-4 / GPT-4o / DeepSeek-V3），大上下文窗口 |
| 上下文策略 | 全量检索（Top-50） + 三轮迭代检索（先粗检→分析结果→再检遗漏） |
| 输出粒度 | 细粒度：逐条需求的详细分析、每个业务规则的精确描述、数据模型的字段级定义 |
| 多轮推理 | 使用 Chain-of-Thought（思维链），要求 AI 逐步推理后再给出结论 |
| 质量验证 | 要求 AI 自我验证分析结果的完整性，补充可能遗漏的内容 |
| 超时控制 | 较长超时（300s），全流式输出 |
| 适用场景 | 核心业务模块的需求分析、高风险变更的影响分析、复杂业务流程的梳理 |

#### 多模型集成模式（Multi-Model Ensemble）

这是最重要的高级模式——使用多个不同的模型对同一任务进行分析，综合各模型的结果以获得更高的准确性和可靠性。

| 特性 | 说明 |
|------|------|
| 目标 | 通过多模型交叉验证，消除单一模型的偏见和盲区 |
| 并行策略 | 多个模型同时调用，各自独立完成任务 |
| 聚合策略 | 见下方详细说明 |
| 模型组合 | 主分析模型 + 验证模型（来自不同提供商，避免同源偏见） |
| 成本 | 为单模型模式的 2-3 倍（按调用的模型数量计） |
| 适用场景 | 核心模块的需求分析、重要测试计划的生成、高风险变更的评估 |

**多模型集成流程：**

```
用户请求（如"分析这份 PRD"）
  ↓
派发到多个模型并行执行（各自独立）
  ├─ Model A (Claude Sonnet-4) → 输出完整分析结果 A
  ├─ Model B (GPT-4o)         → 输出完整分析结果 B
  └─ Model C (DeepSeek-V3)    → 输出完整分析结果 C
  ↓
结果聚合器（Aggregator）
  ├─ 步骤 1：结果标准化 → 将各模型输出转为统一格式
  ├─ 步骤 2：一致性分析
  │   ├─ 高一致性（≥2 个模型结果一致）→ 直接采纳一致结果
  │   ├─ 部分一致 → 标记分歧点，合并公共部分
  │   └─ 全不一致 → 触发调解轮（见下方）
  ├─ 步骤 3：分歧调解
  │   ├─ 将分歧点提交给第四个模型（或用户）仲裁
  │   └─ 或使用投票机制（多数决）
  └─ 步骤 4：最终输出
      ├─ 整合后的分析结果
      ├─ 置信度评分（基于各模型一致性程度）
      └─ 分歧说明（如有）
```

**聚合策略选型：**

| 策略 | 说明 | 适合场景 |
|------|------|---------|
| 投票法（Voting） | 多数模型一致的结果直接采纳，少数分歧标记为"低可信度" | 分类任务、标签提取、优先级判断 |
| 加权融合 | 根据各模型的历史准确率加权合并结果 | 需要定量评估的场景 |
| 最佳选择 | 由仲裁模型从多个结果中选择最优的一个 | 开放性生成任务（用例生成、计划生成） |
| 交叉验证 | Model A 审 Model B 的结果，Model B 审 Model A 的结果 | 用例审查、代码审查 |
| 渐进优化 | Model A 生成 → Model B 优化 → Model C 最终审核 | 需要多轮打磨的场景 |

#### 增量分析模式（Incremental）

| 特性 | 说明 |
|------|------|
| 目标 | 在已有分析结果的基础上，只处理新增或变更的内容 |
| 输入 | 已有分析结果 + 增量文档/文本 |
| 策略 | AI 先对比增量与已有结果，仅处理差异部分 |
| 输出 | 增量更新（新增/修改/删除的条目）+ 无需重新生成全部内容 |
| 适用场景 | 文档更新后的增量需求分析、少量需求变更时的用例补充 |

#### 审查模式（Review）

| 特性 | 说明 |
|------|------|
| 目标 | 使用与生成阶段不同的模型，独立审查已有内容的质量 |
| 模型策略 | 审查模型必须与生成模型不同提供商（避免同源偏见） |
| 独立性 | 审查时不注入生成时的 Prompt 和上下文，仅审查最终内容 |
| 输出 | 审查报告：正确性 / 完整性 / 改进建议 |
| 适用场景 | 重要用例的交叉审查、测试计划的同行评审替代 |

### 通用 AI 调用流程（增强版）

```
用户请求 + 选择分析模式
  ↓
[Step 0] 模式路由 → 根据用户选择的模式确定：
  ├─ 模型选择（单模型 / 多模型 / 本地模型）
  ├─ 上下文检索策略（Top-K 数量、检索深度）
  ├─ Prompt 模板选择（简化版 / 标准版 / 深度版）
  └─ 超时和输出策略
  ↓
[Step 1] 上下文检索 → 从项目上下文中检索与本次请求最相关的信息（检索深度取决于模式）
  ↓
[Step 2] 上下文编排 → 按优先级和相关性编排上下文片段
  ↓
[Step 3] 模型调用
  ├─ 单模型模式：调用选定模型 → 获取结果
  ├─ 多模型模式：并行调用多个模型 → 聚合结果
  └─ Fallback：主模型失败 → 自动切换到备用模型
  ↓
[Step 4] 结果解析 → 结构化输出 / 流式输出（格式取决于模式）
  ↓
[Step 5] 上下文扩展 → （如需）将本次新生成的信息存入项目上下文
  ↓
[Step 6] 返回前端 → 附带分析模式元信息（所用模型、耗时、置信度）
```

## 功能 1：AI 需求分析

- **标识符**: `AI_REQ_ANALYSIS`
- **优先级**: P2（中）
- **依赖**: 用户上传需求文档（PDF / Word / Markdown / 纯文本）；平台已有项目管理
- **输入**: 需求文档文件（可附带目标项目选择和模块标记）
- **输出**: 结构化需求条目列表 + 项目上下文更新

### 需求描述

用户上传一份需求文档（PRD / 产品需求规格），AI 执行三层分析：

1. **文档内容提取**：从文档中提取所有重要内容，不仅限于需求条目，还包括业务规则、数据模型、API 定义、术语解释、架构约束等
2. **项目上下文匹配**：检索该项目已有的项目上下文（历史需求、已有模块、用例等），识别新增需求与历史的交集
3. **上下文感知的需求分析**：结合已提取的文档内容和检索到的历史上下文，输出全面的分析结果——既包含结构化的需求条目，也包含"新增需求与哪些已有模块交叉"的分析说明

提取后的需求条目进入平台的"需求管理"模块，提取的各类重要内容存入"项目上下文"，作为后续所有 AI 功能（测试计划、用例生成、用例检查、测试报告）的知识底座。

### 详细功能点

#### 1.1 文档导入

| 功能 | 说明 |
|------|------|
| 支持格式 | PDF（.pdf）、Word（.docx）、Markdown（.md）、纯文本（.txt） |
| 上传方式 | 前端拖拽上传或文件选择器，支持多文件批量上传 |
| 文档大小限制 | 单文件 ≤ 20MB，总页数 ≤ 200 页 |
| 编码处理 | 自动检测 UTF-8/GBK/Big5，中英文混合场景兼容 |
| 项目关联 | 上传时选择所属项目，AI 自动关联该项目已有的上下文 |

#### 1.2 分析模式选择

用户在发起需求分析前，可选择合适的分析模式：

| 模式 | 适用场景 | 期望耗时 | Token 消耗 |
|------|---------|---------|-----------|
| 快速扫描 | 快速浏览新文档、评估是否值得深入分析 | ~10-30s | 低 |
| 标准分析 | **默认模式**，日常需求文档分析 | ~1-3min | 中 |
| 深度分析 | 核心业务模块 PRD、复杂文档、需全面输出 | ~3-10min | 高 |
| 多模型集成 | 高风险模块、重大变更、需要交叉验证 | ~5-15min | 最高 |
| 增量分析 | 在已有分析基础上补充少量更新内容 | ~10-30s | 低 |

不同模式在以下维度有差异：
- **模型选择**：快速扫描用轻量模型，深度分析用旗舰模型，多模型集成用多个不同模型
- **上下文检索深度**：快速扫描只查 Top-5，深度分析查 Top-50 并迭代检索
- **Prompt 复杂度**：快速扫描用简化 Prompt，深度分析用 Chain-of-Thought
- **输出粒度**：快速扫描只输出主要需求条目，深度分析输出全部内容类型

#### 1.3 AI 分析流程（核心）

```
文档上传 → 文档分块处理
  ↓
[阶段一] 文档内容提取（不局限于需求）
  ├─ 功能需求点       → 提取为需求条目
  ├─ 业务规则 / 逻辑   → 提取为 business_rule 上下文
  ├─ 数据模型 / 字段   → 提取为 data_model 上下文
  ├─ API 定义 / 接口   → 提取为 api_contract 上下文
  ├─ 术语定义          → 提取为 term_definition 上下文
  ├─ 架构/技术决策     → 提取为 architecture 上下文
  ├─ 约束条件          → 提取为 constraint 上下文
  └─ 用户场景          → 提取为 user_scenario 上下文
  ↓
[阶段二] 检索项目已有上下文
  ├─ 对阶段一的每项提取结果，执行语义检索
  ├─ 查找与之相关的历史模块 / 已有需求 / 既有用例
  ├─ 计算关联程度并生成匹配说明
  └─ 输出匹配关系列表
  ↓
[阶段三] 上下文感知的分析报告
  ├─ 将阶段一提取内容 + 阶段二匹配结果一起提交给 AI
  ├─ 要求 AI 站在"已有项目全局"视角重新审视本次需求
  ├─ 标记"新增需求 / 变更需求 / 与某模块重叠"
  └─ 输出最终分析结果
```

#### 1.3 文档内容提取

AI 从文档中提取的内容类型和粒度如下：

| 提取类型 | 说明 | 存储目标 |
|---------|------|---------|
| 功能需求 | 明确的功能点描述，含名称、描述、优先级、验收标准 | requirements 表 + project_contexts（type=requirement） |
| 业务规则 | 业务逻辑约束、计算规则、状态流转条件 | project_contexts（type=business_rule） |
| 数据模型 | 字段定义、数据结构、字段约束、枚举值 | project_contexts（type=data_model） |
| API 契约 | 接口路径、请求/响应格式、错误码 | project_contexts（type=api_contract） |
| 术语定义 | 项目专有名词、缩写、业务术语 | project_contexts（type=term_definition） |
| 架构决策 | 技术选型、系统架构、模块划分 | project_contexts（type=architecture） |
| 约束条件 | 性能目标、安全合规、兼容性要求 | project_contexts（type=constraint） |
| 用户场景 | 端到端的用户操作流程 | project_contexts（type=user_scenario） |
| 业务流程 | 跨模块的业务处理流程、状态机 | project_contexts（type=process_flow） |
| 依赖关系 | 模块间依赖、外部系统依赖、数据依赖 | project_contexts（type=dependency） |

#### 1.5 上下文匹配与历史关联

这是该项目上下文生效的核心环节，确保新增需求能充分利用历史积累：

| 匹配方式 | 说明 |
|---------|------|
| 关键字匹配 | 提取文档中的模块名、功能名词、业务术语，直接匹配已有上下文的 keywords |
| 语义匹配 | 对提取的每个内容片段生成向量，通过 pgvector 检索语义相近的历史上下文 |
| 模块交叉分析 | AI 综合分析："这个需求与订单模块的 XX 功能有交集"、"涉及已有售后流程的扩展" |
| 变更识别 | 对比新旧需求，标记"新增需求"、"需求变更"、"需求移除" |
| 覆盖分析 | AI 检查：本次新增需求是否已被已有功能用例覆盖？是否存在重复？ |

### 数据库模型建议

```sql
-- 需求条目表
CREATE TABLE requirements (
    id SERIAL PRIMARY KEY,
    project_id INT NOT NULL REFERENCES projects(id),
    module_id INT REFERENCES modules(id),
    name VARCHAR(255) NOT NULL,
    description TEXT,
    priority VARCHAR(10) DEFAULT 'P2',     -- P0/P1/P2/P3
    tags JSONB DEFAULT '[]',
    acceptance_criteria TEXT,
    source_file VARCHAR(255),              -- 来源文件名
    source_version INT DEFAULT 1,
    status VARCHAR(20) DEFAULT 'active',   -- active / deprecated / archived
    created_at TIMESTAMP DEFAULT NOW(),
    updated_at TIMESTAMP DEFAULT NOW()
);

CREATE INDEX idx_req_project ON requirements(project_id);
CREATE INDEX idx_req_module ON requirements(module_id);

-- 项目上下文表（详见总体架构章节）
CREATE TABLE project_contexts (
    id SERIAL PRIMARY KEY,
    project_id INT NOT NULL REFERENCES projects(id),
    module_id INT REFERENCES modules(id),
    source_type VARCHAR(30) NOT NULL,
    source_file VARCHAR(255),
    source_version INT DEFAULT 1,
    context_type VARCHAR(50) NOT NULL,
    title VARCHAR(255) NOT NULL,
    content TEXT NOT NULL,
    summary TEXT,
    tags JSONB DEFAULT '[]',
    keywords JSONB DEFAULT '[]',
    embedding vector(1536),
    importance INT DEFAULT 3,
    created_at TIMESTAMP DEFAULT NOW(),
    updated_at TIMESTAMP DEFAULT NOW()
);

-- 分析记录表（记录每次 AI 分析的详情和匹配结果）
CREATE TABLE requirement_analyses (
    id SERIAL PRIMARY KEY,
    project_id INT NOT NULL REFERENCES projects(id),
    document_name VARCHAR(255),
    document_hash VARCHAR(64),               -- 文档内容哈希（用于去重）
    status VARCHAR(20) DEFAULT 'pending',    -- pending / processing / completed / failed
    analysis_result JSONB,                    -- 完整的分析结果（包含上下文匹配信息）
    new_requirement_ids INT[] DEFAULT '{}',   -- 本次新增的需求 ID 列表
    new_context_ids INT[] DEFAULT '{}',       -- 本次新增的上下文 ID 列表
    matched_context_ids INT[] DEFAULT '{}',   -- 匹配到的历史上下文 ID 列表
    created_at TIMESTAMP DEFAULT NOW(),
    completed_at TIMESTAMP
);
```

### 验收标准

- [ ] 上传 PDF/Word/MD 格式的需求文档后，AI 能正确提取需求条目
- [ ] AI 能从文档中提取需求以外的内容：业务规则、数据模型、术语定义等
- [ ] 提取的各类内容正确存入 project_contexts 表，按类型区分
- [ ] AI 在分析时能检索项目已有上下文，识别新增需求与历史模块的交集
- [ ] 分析结果中包含"与已有模块的交叉分析"说明
- [ ] 用户可在"项目上下文"页面查看、编辑、筛选已积累的项目知识
- [ ] 同一项目多次上传文档，上下文持续累积，分析越来越准确
- [ ] 对 50 页以上的长文档能正常处理（分块策略生效）
- [ ] 分析记录可追溯（requirement_analyses 表），清楚知道每次分析匹配了哪些历史上下文

## 功能 2：AI 生成测试计划

- **标识符**: `AI_TEST_PLAN`
- **优先级**: P2（中）
- **依赖**: 功能 1（AI 需求分析），需要有已提取的需求条目和项目上下文
- **输入**: 需求条目列表（来自功能 1）+ 项目上下文
- **输出**: 测试计划文档（测试范围、策略、资源、排期、影响分析）

### 需求描述

基于 AI 需求分析产出的需求条目和项目上下文，AI 自动生成测试计划。在生成过程中，AI 不仅分析本次需求，还会利用项目上下文中的历史模块信息、已有用例情况和历史执行数据，从而给出更准确的回归范围建议和风险评估。

### 详细功能点

#### 2.1 测试范围确定

| 功能 | 说明 |
|------|------|
| 范围分析 | AI 根据需求条目 + 项目上下文，自动识别本次测试涉及的功能模块 |
| 影响分析（核心） | AI 利用项目上下文中的模块依赖关系和架构信息，分析：哪些已有模块可能被本次变更波及，需要纳入回归测试。例如："订单详情页新增售后入口 → 影响订单模块（状态联动）和售后模块（入口配置）" |
| 回归范围推荐 | AI 根据影响分析推荐回归测试范围："全回归" / "受影响模块回归" / "仅增量测试" |
| 排除项 | 用户可手动标记不纳入测试范围的需求或模块 |
| 上下文来源 | AI 自动从 project_contexts 中检索与本次需求相关的 architecture、process_flow、dependency 类型上下文，作为影响分析的依据 |

#### 2.2 测试策略生成

| 功能 | 说明 |
|------|------|
| 测试类型 | AI 推荐需要执行的测试类型：功能测试、回归测试、集成测试、性能测试等 |
| 测试深度 | 根据需求优先级推荐测试深度（冒烟 / 详细 / 全量） |
| 技术建议 | 对于 API 类需求推荐接口测试方案，UI 类需求推荐 UI 自动化方案 |
| 已有用例复用 | AI 检查项目上下文中已有的自动化用例，推荐可直接复用的部分 |
| 历史数据参考 | 如有历史执行数据，AI 参考各模块的历史缺陷率来调整测试策略 |

#### 2.3 资源与排期

| 功能 | 说明 |
|------|------|
| 人力估算 | AI 估算所需人力（人天），基于需求复杂度 + 历史同类需求耗时 |
| 排期建议 | 基于依赖关系给出测试执行排期 |
| 风险预警 | 识别潜在风险（如依赖未就绪、环境不稳定等） |

#### 2.4 测试计划输出

| 功能 | 说明 |
|------|------|
| 输出格式 | 结构化 JSON + 可导出的 Markdown 文档 |
| 影响雷达图 | 可视化展示本次需求对各模块的影响程度（基于项目上下文分析） |
| 编辑能力 | 用户可在前端编辑 AI 生成的测试计划 |
| 版本管理 | 测试计划支持版本记录和变更追踪 |

### 验收标准

- [ ] 基于功能 1 的需求条目和项目上下文，AI 能生成结构化的测试计划
- [ ] 影响分析能基于项目上下文识别"本次变更会波及哪些已有模块"
- [ ] 回归范围推荐有明确的影响分析依据
- [ ] 测试计划包含测试范围、策略、资源估算、排期、风险分析
- [ ] 用户可编辑 AI 生成的计划内容
- [ ] 支持导出为 Markdown 文档

## 功能 4：AI 生成功能用例

- **标识符**: `AI_FUNC_CASE_GEN`
- **优先级**: P0（低）
- **依赖**: 用户上传需求文档或手动输入需求描述
- **输入**: 需求描述 / 需求条目 / 功能描述文本
- **输出**: 功能测试用例（包含步骤、预期结果、优先级、标签）

### 需求描述

用户提供功能需求描述（可以从功能 1 提取的需求条目中选择，也可以手动输入），AI 自动生成功能测试用例。生成的用例包含测试步骤、预期结果、测试数据、优先级和标签。

在生成过程中，AI 会利用项目上下文中的业务规则和数据模型信息，确保生成的用例与项目已有的业务逻辑一致。例如，如果项目上下文中已有"订单状态流转"的业务规则，AI 生成订单相关用例时会自动考虑所有合法状态转换路径。

### 详细功能点

#### 4.1 用例生成模式

| 模式 | 说明 |
|------|------|
| 基于需求条目 | 选择功能 1 中的需求条目，AI 批量生成对应的功能用例 |
| 手动输入 | 用户输入一段功能描述文本，AI 即时生成用例 |
| 批量导入 | 上传需求文档，同时完成需求分析和功能用例生成（合并功能 1） |

#### 4.2 基于项目上下文的增强生成

| 上下文类型 | 对用例生成的影响 |
|-----------|----------------|
| business_rule（业务规则） | 确保用例覆盖所有业务规则分支路径，如"不同等级用户的折扣规则" |
| data_model（数据模型） | 用例中的测试数据自动符合字段约束（类型、长度、格式、枚举值） |
| api_contract（API 契约） | 对于涉及 API 调用的步骤，自动补全请求参数和预期响应结构 |
| user_scenario（用户场景） | 基于已有用户场景生成端到端用例，而非孤立的单功能点用例 |
| constraint（约束条件） | 在用例中体现性能、安全、合规方面的约束检查 |
| process_flow（业务流程） | 用例步骤自动遵循已有的业务流程和状态机定义 |

#### 4.3 用例内容

| 字段 | 说明 |
|------|------|
| 用例名称 | 清晰的功能点描述 |
| 前置条件 | 执行该用例前需要满足的条件 |
| 测试步骤 | 按序号排列的详细操作步骤 |
| 预期结果 | 每一步或最终步骤的预期行为 |
| 测试数据 | 所需的输入数据或测试数据示例 |
| 优先级 | P0-P3，AI 根据需求优先级和业务影响推荐 |
| 标签 | 功能模块、测试类型（正向/异常/边界）等 |
| 关联需求 | 关联到具体的需求条目 ID |

#### 4.3 生成控制

| 功能 | 说明 |
|------|------|
| 用例数量 | 用户可指定每个需求生成多少条用例（如"每个需求至少生成 5 条用例，包含正向和异常场景"） |
| 覆盖方向 | 用户可指定重点覆盖方向：正向流程 / 异常场景 / 边界值 / 权限场景 |
| 批量生成 | 支持选择多个需求条目，一键批量生成 |
| 生成预览 | AI 生成过程中 SSE 流式输出，用户可随时停止 |

#### 4.4 用例管理

| 功能 | 说明 |
|------|------|
| 编辑 | 用户可编辑 AI 生成的任何字段 |
| 批量编辑 | 批量修改优先级、标签、所属模块 |
| 保存 | 确认后保存到平台的"功能用例"模块 |
| 版本 | 保存时生成版本快照 |

### 验收标准

- [ ] 用户选择需求条目后，AI 能生成对应的功能测试用例
- [ ] 生成用例包含完整的测试步骤和预期结果
- [ ] 支持正向、异常、边界等不同场景覆盖
- [ ] SSE 流式输出，用户可看到生成过程
- [ ] 生成的用例可编辑、保存到平台功能用例模块

## 功能 5：AI 功能用例检查

- **标识符**: `AI_CASE_REVIEW`
- **优先级**: P1（低）
- **依赖**: 平台已有功能测试用例（手动创建或功能 4 生成）
- **输入**: 一条或多条功能测试用例
- **输出**: 用例评审意见（问题列表 + 改进建议）

### 需求描述

AI 对已有的功能测试用例进行智能审查，发现用例中的问题（如边界遗漏、步骤不完整、预期不明确、重复用例等），并给出改进建议。

在审查过程中，AI 参考项目上下文中的业务规则、数据模型和已有模块信息，检查用例是否与项目实际业务逻辑一致，是否遗漏了与关联模块的交互场景。

### 详细功能点

#### 5.1 检查维度

| 维度 | 说明 |
|------|------|
| 完整性 | 用例是否有明确的前置条件、操作步骤、预期结果 |
| 正确性 | 预期结果是否合理，操作步骤是否可行 |
| 业务一致性 | 用例是否符合项目上下文中的业务规则？例如，如果业务规则规定"已发货订单不可取消"，但用例中出现了该场景，应标记为"与业务规则冲突" |
| 覆盖率 | 是否覆盖了正向、异常、边界等场景 |
| 重复性 | 多条用例是否覆盖了相同的功能点 |
| 可执行性 | 步骤描述是否清晰，是否包含模糊的表述 |
| 关联性 | 是否遗漏了相关联的功能模块测试（AI 基于项目上下文的模块依赖信息判断） |
| 数据合理性 | 测试数据是否合理、充分（对比项目上下文中的数据模型定义） |

#### 5.2 基于项目上下文的增强检查

| 上下文类型 | 对审查的影响 |
|-----------|-------------|
| business_rule | 验证用例的预期结果是否与已定义的业务规则一致，发现"用例预期与规则冲突"的问题 |
| data_model | 验证用例中的测试数据是否符合数据模型的字段约束（如枚举值范围、长度限制） |
| process_flow | 验证用例的步骤顺序是否遵循已有的业务流程和状态机 |
| dependency | 验证用例是否遗漏了依赖模块的前置条件（如"需要用户已登录"但用例没有前置条件） |

#### 5.3 检查方式

| 方式 | 说明 |
|------|------|
| 单条检查 | 选中一条用例，AI 审查并给出意见 |
| 批量检查 | 选中一个模块或多个模块的全部用例，AI 批量审查 |
| 增量检查 | 新增/修改用例后自动触发审查（可选，Phase 2） |

#### 5.3 输出格式

```json
{
  "case_id": 123,
  "case_name": "用户登录-密码错误",
  "review_summary": {
    "overall_score": 85,
    "issues_count": 2,
    "suggestions_count": 3
  },
  "issues": [
    {
      "severity": "major",
      "category": "completeness",
      "field": "前置条件",
      "content": "缺少前置条件：需要用户已注册且账号状态正常",
      "suggestion": "补充前置条件：用户已注册、账号未被锁定"
    },
    {
      "severity": "minor",
      "category": "boundary",
      "field": "测试数据",
      "content": "未覆盖密码为空的边界场景",
      "suggestion": "增加一条用例：密码为空时提示'请输入密码'"
    }
  ],
  "suggestions": [
    {
      "category": "coverage",
      "content": "建议增加密码连续错误 N 次后账号锁定的场景测试"
    }
  ]
}
```

#### 5.4 前端交互

| 功能 | 说明 |
|------|------|
| 检查按钮 | 用例详情页/列表页的"AI 审查"按钮 |
| 结果展示 | 以弹窗或侧边栏展示审查结果，问题以列表形式呈现 |
| 一键修复 | 用户可点击"采纳建议"，AI 自动修改对应字段（可选） |
| 历史记录 | 每条用例的审查历史可追溯 |

### 验收标准

- [ ] AI 能对单条功能用例给出结构化的审查意见
- [ ] 审查结果包含完整性、正确性、覆盖率等多维度评分
- [ ] 支持批量审查多个用例
- [ ] 审查结果中的问题和建议具体、可操作

## 功能 7：OpenAPI → API 用例

- **标识符**: `OPENAPI_TO_API`
- **优先级**: P0（低）
- **依赖**: 用户上传 OpenAPI 3.0 / Swagger 2.0 规范文档
- **输入**: OpenAPI/Swagger JSON/YAML 文件
- **输出**: API 测试用例（直接映射为平台的 API 自动化用例）

### 需求描述

用户上传 OpenAPI 3.0 或 Swagger 2.0 格式的 API 规范文档，平台自动解析出各 API 端点，生成可直接运行的 API 测试用例。

> **说明**：这是架构文档中已确认的 P0 优先能力。此功能 80% 不需要 AI（结构化解析），20% 用 AI 补充（智能生成断言、参数组合推荐）。

### 详细功能点

#### 7.1 规范解析

| 功能 | 说明 |
|------|------|
| 输入格式 | OpenAPI 3.0 JSON/YAML、Swagger 2.0 JSON/YAML |
| 解析内容 | 路径（path）、方法（method）、参数（parameters）、请求体（requestBody）、响应（responses） |
| 数据提取 | 参数类型、必填/可选、枚举值、默认值、格式约束 |
| 解析方式 | 先尝试结构化解析（基于 openapi-schema-pydantic），对不符合规范的文档回退到 AI 解析 |

#### 7.2 用例生成

| 字段映射 | OpenAPI 来源 |
|---------|-------------|
| 用例名称 | `operation.summary` 或 `operation.operationId` |
| HTTP 方法 | `path[method]` |
| URL 路径 | `path` |
| Headers | `parameters[in=header]` + 安全认证信息 |
| Query 参数 | `parameters[in=query]` |
| 请求体 | `requestBody.content` 的 example / schema |
| 数据类型 | `requestBody.content` 的 content-type |
| 标签 | `operation.tags` |
| 断言（AI） | AI 根据 `responses` 的 schema 和 description 生成默认断言 |

#### 7.3 AI 辅助增强

| 增强点 | 说明 |
|-------|------|
| 智能断言 | AI 根据 response schema 和 description 生成状态码断言 + 关键字段断言 |
| 参数组合 | AI 推荐正常值、边界值、异常值的参数组合 |
| 认证信息 | AI 识别 API 的认证方式（Bearer Token / API Key / Basic Auth）并在用例中预设 |
| 依赖链路 | AI 识别 API 间的调用依赖关系（如"先创建资源再查询"）并排序 |

#### 7.4 批量操作

| 功能 | 说明 |
|------|------|
| 一键导入 | 解析完规范后，用户可一键将所有生成用例保存到平台 |
| 选择性导入 | 用户可勾选部分 API 端点，只导入选中的用例 |
| 模块归类 | 根据 OpenAPI 的 tag 自动归类到对应模块 |
| 覆盖分析 | 显示有哪些 API 端点已被覆盖（已有用例）、哪些是新导入的 |

### 验收标准

- [ ] 上传 OpenAPI JSON/YAML 后正确解析所有 API 端点
- [ ] 生成的 API 用例包含完整的请求配置（method / path / headers / params）
- [ ] AI 能根据 response schema 生成合理的断言
- [ ] 支持 OpenAPI 3.0 和 Swagger 2.0
- [ ] 用户可选择导入全部或部分 API 用例

## 功能 6：AI 功能用例 → 自动化用例

- **标识符**: `FUNC_TO_AUTO`
- **优先级**: P3（极高）
- **依赖**: 功能 4（功能用例）或平台已有功能用例；平台的 Runner 体系已就绪
- **输入**: 功能测试用例（文本描述）
- **输出**: 可执行的自动化测试用例（适配平台的 step 格式）

### 需求描述

将功能测试用例（纯文本描述）自动转换为可执行的自动化测试用例。转换过程需要 AI 理解功能步骤的含义，将其映射为平台支持的 step_type（如 `http_request` / `app_tap` / `app_input` / `assert` 等）。

### 详细功能点

#### 6.1 步骤映射

| 功能步骤类型 | 映射到平台 step_type |
|------------|-------------------|
| "调用 XX 接口" / "发送 XX 请求" | `http_request` |
| "点击 XX 按钮" / "轻触 XX" | `app_tap` |
| "输入 XX 到 XX 字段" / "填写 XX" | `app_input` |
| "滑动到 XX" / "下拉刷新" | `app_swipe` |
| "验证 XX 显示为 XX" / "断言 XX" | `assert` |
| "等待 XX 秒" / "等待 XX 出现" | `app_wait` / `sleep` |
| "打开 XX 页面" / "导航到 XX" | `web_goto` / `app_launch` |

#### 6.2 AI 转换流程

```
功能用例文本
    ↓
步骤分解 → AI 将自然语言步骤拆分为原子操作
    ↓
元素识别 → AI 识别每一步需要的 UI 元素（by/locator）或 API（method/path）
    ↓
步骤类型匹配 → AI 将原子操作映射到平台 step_type
    ↓
参数填充 → AI 从功能用例文本和平台已有配置中提取参数
    ↓
断言生成 → AI 根据"预期结果"生成对应的 assertion 配置
    ↓
测试数据注入 → AI 识别需参数化的数据，标记为变量占位符
    ↓
→ 输出可执行的步骤列表（JSON）
```

#### 6.3 用户交互

| 功能 | 说明 |
|------|------|
| AI 建议 | AI 生成转换后的自动化步骤，用户确认/修改后保存 |
| 步骤编辑器 | 前端提供可视化步骤编辑器（拖拽排序、修改配置） |
| 元素选择器 | 对于 App 操作，提供 by/locator 的辅助选择 |
| 试运行 | 支持在编辑器中单步试运行（需连接设备） |
| 批量转换 | 支持选择多个功能用例，批量转换为自动化用例 |
| 对比模式 | 左侧显示原始功能用例，右侧显示转换后的自动化步骤 |

#### 6.4 智能元素定位（进阶）

| 功能 | 说明 |
|------|------|
| 元素推荐 | AI 根据步骤描述推荐可能的 UI 元素定位方式 |
| 定位兜底 | 当首选定位失败时，AI 建议备选定位策略 |
| 截图辅助 | 用户上传页面截图，AI 辅助定位元素（Phase 2） |

### 验收标准

- [ ] 功能用例转换为 API 自动化用例（`http_request` 步骤）准确率 ≥ 85%
- [ ] 功能用例转换为 App 自动化用例（`app_tap` / `app_input` 等）核心流程可用
- [ ] 转换后的步骤可在平台上编辑和保存
- [ ] 支持批量转换

## 功能 8：AI OpenAPI → 压测

- **标识符**: `OPENAPI_TO_LOADTEST`
- **优先级**: P3（极高）
- **依赖**: 压测基础设施（Locust / k6 / JMeter），功能 7（OpenAPI 解析）
- **输入**: OpenAPI 规范 + 压测配置（并发数、持续时间、Ramp-up 策略）
- **输出**: 压测脚本 + 压测报告

### 需求描述

基于 OpenAPI 规范自动生成压测脚本，并集成到平台的压测执行和报告体系中。用户上传 OpenAPI 规范后，AI 识别核心 API 路径、关键业务流程和压测关注点，生成可直接执行的压测脚本。

### 前置条件：压测基础设施

在实现此功能前，需要先完成压测基础设施的搭建：

| 组件 | 选型建议 | 说明 |
|------|---------|------|
| 压测工具 | Locust（Python 原生，与平台技术栈一致） | 或 k6（性能更好，但需额外学习成本） |
| 压测执行 | Celery worker 独立队列（load_queue） | 与功能/API 测试隔离 |
| 指标存储 | InfluxDB / Prometheus | 存储压测指标数据 |
| 结果可视化 | Grafana / 自建图表 | 展示 TPS、响应时间、错误率等 |
| 压测节点 | 独立机器或容器化部署 | 与被压服务隔离 |

### 详细功能点

#### 8.1 压测场景识别

| 功能 | 说明 |
|------|------|
| 核心路径 | AI 从 OpenAPI 中识别核心业务流程（如"用户登录→浏览商品→下单→支付"） |
| 压测焦点 | 根据 API 的重要性（业务关键程度）和访问频率标记压测优先级 |
| 参数化 | AI 识别需要参数化的字段（如用户 ID、商品 ID，避免压测数据冲突） |

#### 8.2 压测脚本生成

| 功能 | 说明 |
|------|------|
| 脚本格式 | 支持 Locust（Python）或 k6（JavaScript） |
| 场景定义 | 多用户并发执行核心业务流程 |
| 参数化 | 自动处理参数化数据（CSV 数据源或动态生成） |
| 断言 | 压测过程中对响应状态码和关键字段进行断言 |
| Think Time | AI 根据业务场景推荐合理的思考时间 |

#### 8.3 压测配置

| 配置项 | 说明 |
|--------|------|
| 并发用户数 | 用户可设置虚拟用户数 |
| 持续时间 | 压测运行时长 |
| Ramp-up | 用户逐步增加的时间 |
| 目标 QPS | 可选，限制最大 QPS |
| 环境选择 | 选择压测目标环境（dev / staging / prod） |

#### 8.4 压测执行与报告

| 功能 | 说明 |
|------|------|
| 执行 | 通过 Celery 任务派发到 load_queue，在独立节点执行 |
| 实时指标 | WebSocket/SSE 推送：TPS、P50/P95/P99 延迟、错误率 |
| 报告生成 | 压测结束后 AI 生成压测报告（含瓶颈分析、优化建议） |
| 历史对比 | 多次压测结果对比，监控性能趋势 |

### 验收标准

- [ ] 压测基础设施搭建完成（可独立运行压测脚本）
- [ ] AI 能根据 OpenAPI 生成可执行的压测脚本
- [ ] 压测脚本包含核心业务路径的参数化和场景编排
- [ ] 压测执行过程中实时展示 TPS、延迟、错误率指标
- [ ] 压测结束后 AI 自动生成压测报告

## 功能 3：AI 生成测试报告

- **标识符**: `AI_TEST_REPORT`
- **优先级**: P1（低）
- **依赖**: 平台已有测试执行记录（executions / step_executions 数据）
- **输入**: 测试执行结果数据
- **输出**: 自然语言测试报告（摘要 + 分析 + 建议）

### 需求描述

基于测试执行结果，AI 自动生成自然语言的测试报告。报告包含执行摘要、通过率统计、失败分析、趋势分析、质量风险评估和改进建议。

### 详细功能点

#### 3.1 报告内容

| 模块 | 说明 |
|------|------|
| 执行摘要 | 总用例数、通过数、失败数、跳过数、通过率、执行时长 |
| 失败分析 | AI 分析失败用例的根因分类（环境问题 / 数据问题 / 代码问题 / 用例问题） |
| 模块质量 | 按功能模块统计通过率，标注高风险模块 |
| 趋势分析 | 与上次执行、最近 N 次执行对比，展示质量趋势 |
| 风险预警 | AI 识别质量风险，如"某模块连续两次通过率下降超过 20%" |
| 改进建议 | AI 根据失败模式给出针对性建议 |

#### 3.2 报告格式

| 格式 | 说明 |
|------|------|
| Web 在线报告 | 平台内查看，交互式图表 |
| Markdown 导出 | 可导出为 Markdown 文档分享 |
| PDF 导出 | 可导出为正式 PDF 报告（Phase 2） |

#### 3.3 报告配置

| 功能 | 说明 |
|------|------|
| 报告范围 | 可选：单次执行报告 / 模块聚合报告 / 项目周报 / 版本报告 |
| 自动生成 | 执行完成后自动触发报告生成（可选） |
| 手动生成 | 用户选择时间范围和范围，手动触发 |
| 报告模板 | 用户可选择报告风格（详细版 / 简报版 / 管理层版） |
| 定时报告 | 支持定时生成周期报告（每日/每周），通过平台定时任务能力 |

#### 3.4 失败智能分析

| 功能 | 说明 |
|------|------|
| 根因分类 | AI 根据失败日志和步骤输出，自动判定失败根因 |
| 批量归类 | 多条失败用例有相同根因时自动归为一类 |
| 关联变更 | 失败分析关联到最近的项目变更（代码提交、配置变更等）（可选） |

### 验收标准

- [ ] AI 能基于执行结果生成结构化的自然语言测试报告
- [ ] 报告包含执行摘要、失败分析、模块质量统计
- [ ] 失败分析能给出根因分类（环境 / 数据 / 代码 / 用例）
- [ ] 支持导出为 Markdown 格式
- [ ] 多次执行结果支持趋势对比

## 附录：Prompt 模板参考

> 以下为各功能的 Prompt 模板框架，实际详细模板在 AI Gateway 的 `prompts/` 目录中维护。

### 需求分析 Prompt 框架（含项目上下文）

```
你是一个资深的测试需求分析师。请分析以下需求文档，提取其中的重要内容。

## 项目背景
该项目是一个 {{project_name}}，以下是该项目已有的上下文信息：
{{project_context}}

## 文档内容
{{document_content}}

## 你的任务分三部分：

### 第一部分：提取各类重要内容
从文档中提取以下类型的内容（每个类型输出多项）：
1. 功能需求（requirement）— 包含名称、描述、优先级、验收标准
2. 业务规则（business_rule）— 业务逻辑、计算规则、状态条件
3. 数据模型（data_model）— 字段定义、数据结构、枚举值
4. API 合约（api_contract）— 接口定义、请求/响应格式
5. 术语定义（term_definition）— 专有名词解释
6. 架构信息（architecture）— 模块划分、技术选型
7. 约束条件（constraint）— 性能、安全、合规要求
8. 用户场景（user_scenario）— 端到端操作流程
9. 业务流程（process_flow）— 跨模块处理流程、状态流转
10. 依赖关系（dependency）— 模块间依赖、外部依赖

### 第二部分：关联历史上下文
对于第一部分提取的每项内容，判断是否与已有的项目上下文有关联：
- 与哪些已有模块有交集？
- 是否扩展/变更了已有的业务规则？
- 是否涉及已有数据模型的修改？
- 给出每个关联的匹配原因

### 第三部分：输出格式
输出为 JSON，包含：
- new_requirements：[{name, description, priority, module, tags, acceptance_criteria}]
- new_contexts：[{context_type, title, content, summary, keywords, importance, module_id}]
- context_matches：[{context_id, context_title, similarity, match_reason}]
- analysis_notes：[{topic, note}] — 重要的分析发现，如与历史模块的交叉分析

注意：如果项目上下文为空（首次分析），则只执行第一部分和第三部分。
```
