## 🔴 严重（安全 / 可被利用）

### 1. 页面脚本"沙箱"可逃逸 → Celery worker 远程代码执行
`utils/script_runtime.py:compile_script`

用 `exec()` + 限制 `__builtins__` 并不构成真正的沙箱。经典逃逸链在你限制的内建下依然成立：

```python
().__class__.__base__.__subclasses__()   # 拿到所有类 → 找到 subprocess.Popen / os
"".__class__.__mro__[1].__subclasses__()  # 同理
```

`SAFE_BUILTINS` 里保留了 `isinstance/type` 无关紧要——真正的问题是任何对象的 `__class__`/`__mro__`/`__subclasses__` 属性没被拦，攻击者不需要 `__import__` 就能拿到 `os.system`。而这段脚本是在 **Celery worker 进程里**执行的，权限等于整个后端。

谁能触发：`server/api/scripts.py` 里 create/update/test 只需 `dev` 或 `test` 角色（不是 admin）。也就是说一个测试同事的账号被盗 = 整台 worker 沦陷，能读 DB 密码、目标环境凭据、宿主机文件。

建议：真沙箱要么进程隔离（子进程 + seccomp / nsjail / 容器），要么换 RestrictedPython 并显式禁 dunder 属性访问。纯 `exec` 限 builtins 请不要当作安全边界。

### 2. CLI Bug-Fix agent 存在命令注入
`server/services/bug_fix_service.py:210-221`

```python
cmd = self.command.replace("{{prompt}}", prompt)
subprocess.run(cmd, shell=True, ...)
```

`prompt` 由 bug（Task）的标题/描述/复现步骤拼出来，是用户可控内容，被直接插进 `shell=True` 的命令串。只要 bug 描述里带 `$(...)`、反引号或 `;`，就能在仓库目录下执行任意命令。`self.command` 即便是管理员配的模板，注入点在 prompt。

建议：不要把用户内容拼进 shell 字符串。prompt 通过 stdin 或临时文件传给 agent；命令用 `shlex.split` + `shell=False` 的参数列表。

### 3. Appium 服务以 0.0.0.0:4723 暴露且无鉴权
`docker-compose.yaml`（appium 服务 `ports: "4723:4723"`）

Redis/Postgres 你都绑到了 `127.0.0.1`（很好），但 Appium 和 api 是全网卡暴露。开放的 Appium 端点 = 对连接设备/宿主机的任意操作（装 APK、adb shell、文件读写）。局域网内任何人可直连。

建议：Appium 端口也绑 `127.0.0.1` 或放进内部网络（不 `ports` 映射，靠 compose 服务名互访），确需外部访问加反向代理 + 鉴权。

### 4. JWT 默认密钥在非生产环境静默生效 → 可伪造任意用户 token
`server/api/auth.py:30,61-67`

`DEFAULT_SECRET_KEY = "change-me-..."`，只有当 `APP_ENV/ENVIRONMENT/FASTAPI_ENV ∈ {prod,production}` 时才强制校验。任何没设这些环境变量的部署（含很多"其实是生产但没标 APP_ENV"的情况）都会用这个公开的默认密钥签 JWT。知道密钥 = 伪造 `sub=任意user_id` 的 access token，完全绕过登录。

另外 `SECRET_KEY = _get_secret_key()` 在**模块导入时**求值，密钥若来自配置中心（DB），改了要重启才生效——容易和运维预期不符。

建议：无论环境，缺失/弱密钥一律拒绝启动（fail-closed），不要依赖 APP_ENV 这个容易漏配的开关。

### 5. 缺少对象级授权（水平越权 / IDOR）
`server/main.py:189` 全局挂了 `Depends(get_current_user)`，但绝大多数路由**只校验"登录了"，不校验"是不是你的资源"**。

例：`server/api/attachments.py:delete_attachment(att_id)` 拿任意 `att_id` 就删；requirements / cases / config / projects 同理，几乎都没有 project 归属校验。只有零星路由用了 `require_roles`。任何一个最低权限登录账号可以遍历 id 读/改/删全平台数据。

建议：确立"资源必须属于当前用户可访问的 project"这一层校验，做成统一依赖，而不是逐个路由靠自觉。

## 🟠 中等

### 6. 附件允许 SVG 且按静态资源原样返回 → 存储型 XSS
`server/api/attachments.py:42`（`.svg` 在白名单），main.py 用 `StaticFiles` 挂 `/attachments`。

SVG 可内嵌 `<script>`。用户上传恶意 SVG，别人访问 `/attachments/req_x/xxx.svg` 时在你的域下执行脚本。而 token 存在 `localStorage`（见 #8），XSS 可直接偷 token。

另外校验只看**扩展名**，不看 magic bytes / content-type，`.png` 里塞 HTML 一样能骗过（虽然浏览器嗅探行为不同）。

建议：SVG 从白名单去掉，或对下载响应统一加 `Content-Disposition: attachment` + `Content-Type: application/octet-stream` + `X-Content-Type-Options: nosniff`，让附件永远"下载"而非"内联渲染"。

### 7. 登录无限速 / 无锁定 → 可暴力破解
`server/api/auth.py:login`

没有失败计数、锁定、验证码或限速（全仓 grep 无 rate limit）。配合 bcrypt 虽慢，但弱口令依然可被在线爆破，且没有告警。

建议：加登录失败节流（按用户名+IP），多次失败短暂锁定，记录审计日志。

### 8. access/refresh token 存 localStorage
`frontend/src/lib/api.ts:129-156`

localStorage 对 JS 完全可读，任何 XSS（见 #6）都能盗走长效 refresh token（14 天）。

建议：至少 refresh token 走 `HttpOnly + Secure + SameSite` cookie；access token 短期留内存。这是老问题、权衡取舍，但结合 #6 风险被放大。

### 9. 附件的 `uploaded_by_id` 由前端 Form 传入、可伪造
`server/api/attachments.py:98,108`

"谁上传的"取自请求体而不是 `current_user`，客户端可随便填。审计信息不可信。

建议：直接用 `current_user.id`，去掉这个入参。

### 10. CORS 默认 `*`
`server/main.py:_cors_origins`（默认 `["*"]`）

开发方便可以理解，但默认值是"放开"。当前用 Bearer 而非 cookie，危害有限；一旦将来改用 cookie 认证，这就是 CSRF/跨域读取的口子。

建议：默认收紧为空/显式白名单，开发环境显式放开。

### 11. DB 默认口令 `tap_pass` 进了 git
`config/object_conf.ini:23`、`docker-compose.yaml`（`${DB_PASSWORD:-tap_pass}`）

作为 bootstrap 默认可以理解，但它 git-tracked 且到处复用。很多部署不会去改。

建议：默认值设成会导致启动失败的占位符，强制部署方显式提供；`object_conf.ini` 从版本库移除、只留 `.example`。

## 🟡 设计 / 架构 / 可维护性

### 12. Runner"永不 raise"契约容易掩盖真 bug
`runners/protocol.py` 约定所有异常包成 `StepResult(ERROR)`。方向对（用例不该因框架异常崩），但代价是：框架自身的编程错误（如 None 解引用、注入对象类型不对）会被"降级"成一条 ERROR step，排查时看不到真正的 traceback 归属。建议区分"用例失败"与"框架内部错误"两类，后者仍要显著上报/告警。

### 13. SQL step 靠字符串 `;` 分割 + `${var}` 文本替换
`runners/steps/sql_exec.py:51,76`

`${var}` 是文本 `rep_expr` 替换后直接拼进 SQL，不是参数化。teardown 场景变量多来自前序 extract，但只要某个 extract 值可被外部影响，就是 SQL 注入。且用 `;` 切分语句本身脆弱（字符串字面量里有分号就会被错误拆开）。属于测试平台"设计如此"的取舍，但要清楚这是信任边界。

### 14. `_get_secret_key()` 等在模块导入期做副作用
`server/api/auth.py:67`

import 期读配置/DB、算密钥、甚至可能 `raise RuntimeError`。让模块 import 有了运行时依赖，单测和工具链 import 该模块都会触发。建议改成惰性获取（函数内取）或应用启动钩子里做。

### 15. 多处 `except Exception: pass` / 宽异常吞掉
`utils/script_runtime.py` 的 `_find_script`、`list_script_names` 等 `except Exception` 后返回空/None。DB 抖动、脚本表结构变更等错误被静默吞掉，表现为"函数莫名找不到"，难排查。建议至少 `logger.warning` 记录（部分地方已记，保持一致）。

### 16. `spa_fallback` catch-all 的静态文件返回未做路径校验
`server/main.py:spa_fallback`

`candidate = FRONTEND_DIST / full_path; if candidate.is_file(): return FileResponse(candidate)`。虽然 Starlette 对 path 参数一般已归一化，但这里是自己拼路径再返回文件，建议显式校验 `candidate` `resolve()` 后仍在 `FRONTEND_DIST` 之内，防目录穿越（`..%2f` 之类）回归。

### 17. 无 Python lint/format 一致性保障（你们自己也标注了）
仓库有 `ruff.toml` 但 CLAUDE.md 说"没有 lint 配置"，两者矛盾——说明 ruff 是后加的、可能没接入 CI。建议把 ruff 接进 Jenkinsfile/pre-commit，否则风格与低级错误只能靠 review。

### 18. Alembic 自动生成迁移易漏 server_default / index
CLAUDE.md 自己点了这个 trap，但没有防护机制。建议 CI 加一步"迁移与模型漂移检测"（`alembic check` 或对比 autogenerate 空 diff），否则迟早出现库结构和模型不一致。

## 交互 / 产品逻辑层面的小盲点

- **改密码后吊销全部会话**（auth.py:432）体验上会把当前设备也踢下线，前端若没处理会突然 401。确认登录页有平滑重登流程。
- **admin 账号禁止改密码**（auth.py:422）意味着内置 admin 口令一旦泄露无法自助更换，只能改库。考虑允许改、但保留"不可删/不可停用"。
- **refresh 接口不轮换 refresh token**（auth.py:refresh 只发新 access token）。长效 refresh token 一旦泄露，14 天内持续有效且无法通过正常刷新使其失效。建议 refresh 时轮换（rotation + 复用检测）。

## 建议的处理顺序

1. 先堵 RCE/注入面：#1 脚本沙箱、#2 命令注入、#3 Appium 暴露、#4 JWT 默认密钥。
2. 再补授权与 XSS：#5 对象级授权、#6 SVG/附件、#8 token 存储。
3. 然后是防爆破 #7、审计 #9、CORS #10、密钥入库 #11。
4. 架构/工程化项（#12–18）纳入常规迭代。
