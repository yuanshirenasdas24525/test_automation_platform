## ADR-01 浏览器接入方式 【已定版】

**问题**：Web 录制用平台新起的浏览器，还是连接用户已有 Chrome？

**决策**：仅支持平台通过 Playwright 启动的受控浏览器。默认 Chromium，新建录制向导中可选 Chromium / Firefox / WebKit（Playwright 多内核适配成本低）。

**排除项**：连接用户已有 Chrome（浏览器扩展或 CDP 接入）明确排除出 MVP，作为远期能力另立需求。

**理由**：受控浏览器的事件注入、快照采集、生命周期管理都可控；接管用户浏览器涉及扩展分发、版本兼容和会话污染，复杂度不成比例。

## ADR-02 移动端操作方式 【已定版】

**决策**：移动端录制仅支持平台远程画面操作——用户在录制工作台的设备画面上点击/滑动，由平台经 Appium 转发执行，从而精确关联目标元素。不监听用户对真机的物理触摸。

**理由**：直接触摸真机时平台只能感知"页面变了"，无法稳定确定用户点击了哪个元素，动作-元素关联链路断裂。

**代价与缓解**：画面刷新延迟直接影响操作体验；阶段 0 必须实测刷新周期能否压到 200～300ms（见需求文档 FR-03），达不到则在产品层管理体验预期。

## ADR-03 快照文件存储 【已定版】

**决策**：MVP 使用本地共享 Volume 存储快照文件（截图、原始树、规范化树），但必须通过统一的 `StorageService` 接口（save_file / get_file / delete_file / exists）封装，业务代码禁止直接拼接文件路径读写磁盘。

**理由**：本地部署背景下对象存储是过度设计；接口抽象保证后续切 MinIO/OSS 时只换实现不动业务层。

## ADR-04 数据保留策略 【已定版】

**决策**：去重后的唯一页面快照及关联数据永久保存，系统不做自动过期清理；仅允许用户手动删除，删除必须记录审计日志（删除人、时间、对象、级联范围），不可恢复。实时画面的连续帧（500ms～1s 截图流）不属于保存范围，会话结束即丢弃。

**背景假设**：小规模本地化部署，一个项目全量录制一次、随 UI 变更增量补录，总量可控。

## ADR-05 定位器维护方式 【已定版】

**决策**：禁止手工修改正式定位器。定位器只能通过重录或**单页面补录**（针对单个逻辑页面的轻量录制会话）更新，保证每个定位器都有快照证据背书。

**理由**：允许手改会让"元素事实库"退化成"元素猜测库"，失去与视觉/结构证据的绑定，版本对比和失效分析全部失真。

## ADR-06 AI 生成用例的前提 【2026-08-14 修订】

**决策**：Web UI 自动化生成支持两种来源模式：

1. `功能用例 + 元素库`（推荐）：功能用例承载业务意图、前置条件和预期，元素库提供页面、元素、定位器与录制链路事实；
2. `仅元素库`（冷启动/补充）：没有功能用例时，只允许根据真实页面、元素、录制动作和跳转关系生成证据充分的 smoke、导航、表单与页面状态用例。

两种模式均必须记录模型、Prompt 版本、Token、来源页面/快照/元素证据。AI 只能引用真实 `element_id`，不得直接产出或覆盖 CSS/XPath；缺少元素事实时必须生成待补录/人工接管项，不能猜测定位器。仅元素库模式的可信度低于联合模式，并在草稿中明确显示。

**理由**：联合模式仍是质量上限和默认入口；但项目冷启动或功能用例尚未沉淀时，不应阻断基于已录制事实的自动化资产产出。后端事实编译与人工评审可以守住可执行性下限。

## ADR-07 UI 地图展示形态 【已定版】

**决策**：MVP 采用列表视图 + 跳转关系表格（页面列表、每页入边/出边）。图形化节点连线地图（React Flow 方案）后续独立立项、另出需求文档。数据模型与 API 对两种展示形态通用。

**补充（v1.1）**：需求文档 v1.3 新增的"页面漫游视图"（FR-16，截图热区可点击、沿跳转边导航）是第三种展示形态，同样复用本数据模型，不改变本决策对图形化节点图的排期判断。

## ADR-08 WebView / Hybrid 支持 【已定版】

**决策**：支持，纳入阶段 2（Android）/ 阶段 3（iOS）正式范围；阶段 2 排期相应扩为 3～4 周。

**硬性前提**：被测 App 的 WebView 必须开启 `setWebContentsDebuggingEnabled(true)`（阶段 0 必验：确认能拿到带调试开关的测试包）；iOS 侧依赖 Safari Remote Debugging（Simulator 默认可用，真机需开 Web 检查器）。

**兜底**：WebView 能力交付前的中间版本，遇到 WebView 页面必须明确标记"WebView 区域，暂不支持元素采集"，不得静默出错。

## ADR-09 网络请求录制 【已定版】

**决策**：录制网络请求。阶段 1 先落地"网络空闲"页面稳定信号；接口断言生成后置。

## ADR-10 部署架构 【已定版】

**决策**：macOS 宿主机混合部署。Android Emulator、iOS Simulator、Appium Server 在宿主机原生运行（**禁止写入 docker-compose**）；FastAPI / PostgreSQL / Redis / Celery / 前端继续跑 Docker Compose，容器内经 `host.docker.internal:4723` 访问宿主机 Appium。

**硬性理由**：iOS Simulator 依赖 Xcode 与 macOS 系统框架，无法容器化；macOS 上的 Docker 运行于虚拟机、无嵌套虚拟化，Android Emulator 在其中无硬件加速。

## ADR-11 API↔Recorder 控制通道 【已定版】

**问题**：录制是长会话 + 交互式控制。REST 控制请求（start / pause / perform_action / capture_snapshot / stop）到达 FastAPI 进程，而 Playwright/Appium Session 对象存活在录制进程中；Celery 无法把任务定向路由到"持有该 Session 的特定 Worker 进程"，因此"专用 Celery Worker 管理录制 Session"在没有可寻址机制之前不可行。实时画面帧回传（录制进程 → API → 前端 WebSocket）同样需要跨进程通道。

**候选方案**：

| 方案 | 说明 | 优点 | 缺点 |
|---|---|---|---|
| A. Recorder Agent（推荐） | 每个录制节点一个小型 HTTP/WS 服务进程，API 按 `agent_id` 转发控制命令 | 寻址天然成立（同 Appium Server 模式）；生命周期独立；契合 ADR-10 宿主机部署 | 新增常驻进程的部署/健康检查/鉴权 |
| B. Worker 内命令队列 | Worker 内线程持 Session、消费 Redis 命令队列（每会话一个 key） | 不新增进程形态 | 占用 Worker 槽位 30 分钟级；重启恢复复杂；命令与帧全走 Redis 链路长 |

**决策**：采用方案 A。Recorder Agent 由 `start-dev.sh` 在 macOS 宿主机启动，持有 Playwright/Appium 长会话；FastAPI 通过 HTTP 控制并按序号增量拉取事件。Agent 可通过 `UI_RECORDER_AGENT_SECRET` 和 `X-Recorder-Secret` 使用共享密钥鉴权。首个版本采用 1～2 秒轮询截图/事件，不引入 Redis 定向队列；需要更高帧率时再升级 WebSocket 帧通道。

## ADR-12 Web Recorder 部署位置与有头模式 【已定版】

**问题**：需求文档 12.1 要求 Playwright 有头模式 + 注入监听器捕获用户真实操作；但按 ADR-10，Celery Worker 在 Docker 容器内（无 DISPLAY），现有 `runners/web/adapters.py` 的 PlaywrightAdapter 在无 DISPLAY 时强制降级 headless——"用户直接操作弹出的有头浏览器"在容器内不成立。

**候选方案**：

| 方案 | 说明 | 优点 | 缺点 |
|---|---|---|---|
| A. 宿主机原生运行（推荐） | Web Recorder 与 Appium 同侧原生跑（配合 ADR-11 的 Agent 形态），有头浏览器弹在用户桌面 | 操作真实浏览器、事件注入捕获、体验最好；契合本地化部署 | 录制绑定宿主机环境；宿主机需装 Playwright 内核 |
| B. 容器内 headless + 画面转发 | Web 端操作也走 ADR-02 式远程画面转发 | 部署统一；适配远期远程/多用户 | 交互延迟；事件注入方案作废 |

**决策**：采用方案 A。Web Recorder 原生运行在宿主机，默认打开有头 Playwright 浏览器；容器只保存控制面和录制结果。方案 B 仅作为未来远程节点能力记录。

## ADR-13 技术上下文保留 【已定版】

**决策**：录制会话事件、去重后的页面/模拟器快照、定位器证据和离线包随项目保留，默认不自动过期；连续实时帧不永久保存。密码、Cookie、Authorization、API Key 等在 Agent 侧先脱敏，单正文和单会话制品均设容量上限。删除项目或录制会话时按外键级联删除元数据，制品清理通过后续 StorageService/审计任务完成。

## ADR-14 移动端网络采集边界 【已定版】

**决策**：Web 必须采集 XHR/Fetch 并用于本地 Mock。Android/iOS Native Network 只有在测试代理或应用内 SDK 已配置时才承诺请求正文；未配置、证书固定或驱动不支持时，必须在环境事件和界面展示明确的降级原因，不得伪装成“已采集且无请求”。首个移动端切片采集画面、UI Tree、远程动作、设备日志和环境，Native Network 标记为降级。

## ADR-15 主录制基线与补充会话 【已定版】

**问题**：项目级元素库会聚合多次录制，但离线包、页面快照和接口 Mock 原本按单次会话隔离。固定使用“最新会话”会导致页面属于旧会话、Mock 属于另一会话，出现页面归属校验失败或离线 `599` 未命中。

**决策**：每个项目、每个平台最多存在一个主录制基线。原始录制会话保持不可变，并分为：

- `primary`：主录制，提供默认元素库页面和离线交互基线；
- `supplement`：补充录制，完成后先进入待合并状态，人工确认后加入主基线；
- `history`：独立历史录制，只用于版本回顾，不影响当前主基线。

主基线保存版本号，但不复制或覆盖原始制品。离线回放启动时动态组合主录制和所有已合并补充录制的页面、资源与 XHR/Fetch Mock；当前所选页面的来源会话优先提供同名页面、静态资源和 Mock，其余会话只补缺。页面状态必须同时携带快照指纹与来源会话 ID，防止相同指纹跨会话时选错版本。

**合并策略**：首次完成的录制可成为主录制；后续补充录制默认不自动覆盖主基线，用户通过“合并到主基线”发布新版本。可以将已完成历史/补充录制提升为新主录制，旧主录制转为已合并补充，从而保留回滚证据。主录制不能直接删除，必须先提升其他完成态录制。

## ADR-16 离线交互、元素定位与 Web AI 安全探索 【已定版】

**问题**：元素库既要像真实页面一样连续交互，也要像浏览器开发者工具一样精确定位元素。用“一次性临时交互”在两个状态间自动跳转不符合用户直觉，也不利于连续完成业务流程；完全依赖人工录制又会遗漏未访问页面。同时，离线 DOM 中由 React Portal 创建的弹窗可能已经失去框架事件监听，点击关闭后会被静态快照恢复。

**决策**：

- Web 元素库打开页面后默认启动离线回放并进入持续交互状态，按钮、输入框、弹窗和路由跳转按真实离线业务流程执行，不再提供“一次性临时交互”。
- 工具栏提供与浏览器开发者工具相似的元素定位图标。开启后离线业务交互立即停用，鼠标悬停实时高亮候选元素并展示标签、语义名称和尺寸，点击只锁定元素及其定位器；再次点击图标退出定位并恢复离线交互。两种模式必须互斥。
- Web 提供“AI 探索录制”，但实现为受确定性安全门禁约束的语义探索器：限定同域、最大页面数、最大深度、单页动作数和总时长；只进入链接、导航、标签、菜单、展开/收起和明确的查看类动作。
- AI 探索自动继承同项目已完成录制中的同域页面作为安全种子，再继续从 DOM 发现新路由；历史 URL 的敏感参数、缓存参数和外域地址在进入 Agent 前移除。
- AI 探索与人工 Web 录制复用同一个 Recorder Runtime，统一采集画面、Console、XHR/Fetch、动作、URL、环境、元素和离线页面，不维护一套简化录制旁路。
- 密码和登录态不由探索器读取、猜测或保存。遇到登录页时暂停并等待用户在受控浏览器中人工登录，成功后继续。
- 删除、停用、退出登录、运行、发布、提交、保存、新建、编辑、上传、下载、支付、重置、确认等危险动作，以及表单提交和未知按钮一律跳过；安全门禁不能被 AI 排序或后续模型调用绕过。
- 探索结果保存为新的主录制或补充录制；已有主基线时默认是补充录制，不自动合并或覆盖当前离线基线。
- 对失去框架监听的离线 Portal 弹窗，优先等待原事件处理；动作后弹窗仍存在时，只清理当前弹窗及关联遮罩并恢复根节点可交互状态。该兜底不执行任意页面脚本，也不放宽严格离线网络边界。

**范围**：首期只支持 Web。Android/iOS 的自动探索需要单独定义设备动作风险、系统弹窗和应用重置策略，不复用 Web 门禁直接上线。
