# 改造方案:用例生成的上下文注入(P0-1)

> 2026-07 | 对应路线图 P0-1 | 状态:方案待评审

## 现状盘点(读码结论)

M7 生成链路 `_handle_functional_case_gen`(tasks/ai_tasks.py:632)→ `build_case_generation_context`(server/services/case_generation_context_builder.py)目前注入:

- 需求字段 + 模块信息 + 依赖/子需求(base context)
- 附件文档摘录 + UI 截图(vision 优先 / OCR 回退)
- 最新 AI 分析文档 markdown
- **同需求**已有用例的**标题**(仅标题,仅本需求)
- scenario_mix / user_prompt

另一条两段式链路(server/api/functional_cases.py:1307/1481/1875,outline → batch,含 interface 模式)注入内容类似。

## 缺口(按影响排序)

### 缺口 1:project_contexts 记忆层完全没接 ⭐ 最大低垂果实
`database/models/project_context.py` 已定义 10 类上下文(business_rule / data_model / api_contract / term_definition / process_flow / constraint...),`context_service.retrieve_context()` 检索函数现成,**但只有 M6 requirement_parse 在用,M7 用例生成没接**。这意味着生成用例时 AI 看不到业务规则、字段定义、术语表——正是"生成废话用例"的直接原因。

### 缺口 2:few-shot 只有标题没有样例
`EXISTING_CASE_TITLES` 只给标题,AI 学不到本项目用例的粒度和风格;且范围只有"同需求",跨需求防重复失效。已被人工采纳的草稿(质量金标准)完全没利用。

### 缺口 3:interface 模式没有真实 API 事实
接口用例生成(interface_case_batch)没有注入真实 endpoint / 参数 schema,AI 可能虚构接口和字段——这类用例静态校验都过不了,是"跑不起来的垃圾"主要来源。`coding_agent/rag`(BM25 + embedder + retriever,code_chunk 索引)已具备但只服务 bug_fix。

## 改造方案

### Phase A:接入记忆层(1–2 天,先做)

1. `build_case_generation_context` 增加一步:
   ```python
   matched = retrieve_context(
       query_text=req.title + "\n" + (req.description or "")[:500],
       project_id=req.project_id,
       top_k=8,
       target_types=["business_rule", "data_model", "api_contract",
                     "term_definition", "process_flow", "constraint"],
   )
   ```
2. 新增占位符 `{{PROJECT_CONTEXT}}`(用现成的 `build_context_summary` 渲染),写进 `case_generation_v1.md`,加一句指令:"以下是项目沉淀的业务规则与数据定义,用例中的字段、状态、流程必须与之一致"。
3. 同样接入 functional_cases.py 的 outline / batch 两段式链路(outline 阶段注入即可,batch 阶段带 outline 已含)。

### Phase B:few-shot 样例升级(1 天)

1. 新增 `{{EXEMPLAR_CASES}}`:取**同模块**最近被 commit 的 2–3 条完整用例(title + steps_text + expected + step_template JSON),作为"本项目风格金标准"。数据源优先 `ai_case_drafts(status=committed)`,不足时补人工用例。
2. `EXISTING_CASE_TITLES` 范围从"同需求"扩到"同模块"(上限 30 条),防重复才有意义。

### Phase C:interface 模式注入 API 事实(2–3 天)

按可得性降级取材,渲染进新占位符 `{{API_FACTS}}`:

1. `project_contexts` 中 `context_type=api_contract` 的条目(Phase A 已检索到)
2. `coding_agent/rag` retriever 按需求关键词检索路由/schema 代码块(复用 bug_fix 的索引)
3. (远期)支持导入 OpenAPI 文档直接入 project_contexts

Prompt 加硬约束:**"只允许使用下列真实接口;若所需接口未列出,生成 `needs_api_detail=true` 标记而不是虚构 endpoint/字段"**——给模型留"承认不知道"的出口,比禁止更有效。

### Phase D:效果验证(半天,连任务 #8)

`ai_runs` 已存 `prompt_hash` / `prompt_version`。注入上线时 bump prompt_version,按版本对比**草稿采纳率**与**编辑距离**——这是判断注入是否真有效的唯一标准,不靠感觉。

## 实施注意(项目 trap 对照)

- token 预算:每个注入块设 MAX_CHARS 截断(仿 `MAX_ANALYSIS_MARKDOWN_CHARS` 先例),PROJECT_CONTEXT 建议 ≤4000 字符
- `_render_prompt` 占位符必须全量渲染,模板加占位符时同步改 placeholders dict,否则渲染残留 `{{}}`
- retrieve_context 当前是关键词打分而非向量检索——先接上用,效果不够再切 pgvector(embedding 列已预留),不要一开始就重构检索
- 验证用 EAGER 模式(`CELERY_TASK_ALWAYS_EAGER=1`)直跑,print 落 uvicorn 终端
- 记忆层是空的项目注入了也没用:前置依赖是该项目跑过 M6 requirement_parse;`build_case_generation_context` 里对空结果渲染"(项目暂无沉淀上下文)"即可,不要报错
