# AI 用例质量 —— 实施方案

> 2026-07-20 | 基于报告 8（163 条 api 用例）的实测诊断制定
> 关联文档：[AI用例质量路线图.md](./AI用例质量路线图.md)（目标与指标） · 本文是落地方案

## 一、问题诊断（实测数据，非推测）

对项目 1 的 163 条 api 用例做变量闭合分析，并与报告 8 的执行结果交叉验证：

| | 通过 | 失败 |
|---|---:|---:|
| 变量闭合的用例（56 条） | **36** | 20 |
| 存在悬空变量的用例（107 条） | **0** | 106 |

**结论：悬空变量的用例通过率恒为 0，占全部失败的 84%。** 这不是"AI 生成质量普遍差"，
而是一个单一缺陷类 —— 缺少一道变量闭合校验。

### 根因链

平台**有**跨用例变量池（`tests/service_run_executor.py::_RUN_SHARED_VARS`，每条用例执行完
回写、下一条注入），机制本身是好的。塌的是地基：

```
case 353「前置链-创建超级用户并获取admin_token」
  step0  POST /api/users
         Authorization: Bearer ${admin_token_pre353}   ← 无人产出（鸡生蛋：要 admin_token
                                                          才能建号，而这条用例正是去拿它的）
  且该用例 extract 为空 —— 即使成功也产不出 admin_token
       ↓
  前置链失败 → admin_token / test_username 从未进入共享变量池
       ↓
  103 条引用 ${admin_token}、65 条引用 ${test_username} 的用例 → 全部 401
       ↓
  反复失败登录 → 触发平台自身限流 → 429 再带崩十余条
```

### 现有 AI 修复为何救不了

`server/services/ai_fix_service.py` 诊断侧够用（`:330` 已能算出"变量无人产出"），
卡在执行侧三道门：

1. `_apply_fix_to_case` 只有 4 种动作（extract / assertion / params / headers），
   全是"改现有步骤字段"，**没有"增加步骤"**；
2. 预检 `:580` 会 drop 掉引用了无前序产出方变量的 fix；
3. 诊断 prompt 7.3 明令"无候选时只在 findings 提示用户，禁止 `fix.pre_hook`"。

结果：正确分类 + findings 写"请自己加登录步骤" + `fix` 为空，**一条也修不了**。

## 二、总体架构：三道闸门

```
① 生成侧闸门 ── 不让坏用例入库（治增量）
② 运行时闸门 ── 补前提 + 辨真伪（核心）
③ 修复侧闸门 ── 治存量 + 补 AI 能力
```

核心原则：**越靠前越便宜**。能在生成时挡住的不留到运行时；能用确定性规则判定的不烧 LLM。

## 三、阶段 1｜生成侧：变量闭合闸门

| 改动 | 位置 | 说明 |
|---|---|---|
| 接口用例校验器 | `server/services/draft_validation.py` | `validate_interface_draft()`：按执行顺序模拟，维护 produced 集合（`default_parameters` ∪ 各步骤 `extract_data`/`extract`），每个 `${var}` 必须已产出 |
| 鸡生蛋检测 | 同上 | 用例声称产出 X 却在自己第一步引用 X（case 353 的病） |
| 接入自修回路 | `ai_case_generation` 链路 | 校验不过 → 打回让模型自修（回路已有） |
| 前置链模板化 | 新增 `server/services/precondition_builder.py` | 前置链是地基，不交给 LLM 自由发挥：确定性代码生成「登录 → extract token → 建号 → extract 用户名」，凭据取自 `auth_provider`（与阶段 2 共用配置） |

**验收**：新生成 100 条用例变量闭合率 100%；评审页不再出现悬空变量用例。

## 四、阶段 2｜运行时闸门

### 2.1 自动鉴权补齐（A 类 · 确定性 · 两种运行模式都生效）

配置中心新增 `auth_provider` 配置组，每个项目配一次：

```yaml
auth_provider:
  path: /api/auth/login
  params: {username: "${user_admin}", password: "${password_admin}"}
  extract: {admin_token: "$.data.access_token"}
```

`runners/case_executor.py` 在 `_inject_variables` 之后执行 `_ensure_auth_vars()`：

```
扫描本用例所有步骤引用的 ${var}
  → 找出既不在 ctx.vars、也不在 default_parameters 的悬空变量
  → 命中鉴权语义（token / auth / jwt / access_token / credential …）
  → 用 auth_provider 登录一次产出该变量
  → 结果进 RunAuthCache，全轮复用（天然规避限流）
  → 报告标注「已自动补齐鉴权：admin_token」
```

**这一条零改动救活当前 103 条用例，且不消耗 token。**

与"禁止隐藏逻辑"原则不冲突：它是用户**显式配置的、全局统一的、报告中可见的**规则，
而非 AI 每条用例即兴发挥的暗箱。

### 2.2 双运行模式

| | 正常运行 | AI 辅助运行 |
|---|---|---|
| 确定性 | 完全确定、可复现 | 含 AI 判断 |
| AI 介入 | 不介入 | 分诊 + 影子验证 |
| 用例库 | 不改 | 不改（见 2.4） |
| 适用 | CI / 回归闸门 / 日常 | 排查、用例治理 |

改动：`RunTestRequest` 加 `ai_assist: bool = False`；`TestReport` 加 `run_mode`
（`normal` / `ai_assisted`，需迁移）；前端双按钮 + 报告 badge。
**CI / 定时任务锁死 normal 模式**，防止 AI 判断混入质量闸门。

### 2.3 失败分诊：分层判定

先确定性、后 LLM —— 大部分判别不需要模型：

| 层 | 判据 | 结论 | 成本 |
|---|---|---|---|
| **L1** | 响应树里**搜得到**目标值，仅路径写错（`find_jsonpath_candidates` 已有） | 用例问题 · JSONPath | 0 |
| **L1** | 变量未解析且全局无产出方 | 用例问题 · 缺前置 | 0 |
| **L1** | 5xx / 连接失败 / 超时 | 环境问题 | 0 |
| **L1** | 负向用例（【参数校验】【鉴权】…）+ 4xx 符合断言 | 正常 | 0 |
| **L2** | 响应结构正确但值不符业务规则 | **接口问题** | LLM |
| **L2** | 断言过松（HTTP 200 但业务码失败）/ 过严 | 用例问题 · 断言 | LLM |

判别 JSONPath 写错 vs 接口问题的核心信号：**响应里到底有没有这个值**。
有 → 用例写错；没有（或 5xx / 业务码失败）→ 接口问题。
`build_case_hints` 已能算出该信号，当前仅作为"线索"喂给 LLM，未直接用于定性。

### 2.4 影子验证（B 类安全阀）

分诊为「用例问题」且有候选修复时：

```
原步骤仍记为失败（结论不变，报告是红的）
  → 用候选修复影子跑一次
  → 影子结果不覆盖原结果
  → 报告附「此修复已验证可用」+ diff
  → 用户评审采纳后才落库
```

**为什么运行时不直接改用例库**：一旦自动改断言，绿色不再证明系统正确，只证明
AI 让它变绿了 —— 真 bug 会被"修复"掩盖，回归网破洞而不自知。影子验证保留运行时效率
（省掉"应用 → 重跑 → 比对回滚"往返），同时把决策权留给人。

> 可选的 `auto_apply=true` 激进模式前提：仅限 L1 确定性分类、全程审计、一键整批回滚、
> normal 模式永不启用。

### 2.5 报告呈现

- 双通过率：**真实通过率**（normal 口径，进指标）+ **修复后可达通过率**（参考值）
- 每条失败标注：分类（用例问题 / 接口问题 / 环境 / 正常）+ 是否有已验证修复

## 五、阶段 3｜修复侧

| 改动 | 说明 |
|---|---|
| 确定性批量修复 | 鉴权类经 2.1 自动解决；其余模式化缺陷（JSONPath 明显错）用 `find_jsonpath_candidates` + 最近报告真实响应批量修 |

## 五之二、落地记录（2026-07-22 ~ 23）

### 实测效果（项目 1，用例级口径）

| 阶段 | 通过 / 163 | 通过率 |
|---|---:|---:|
| 起点（报告 8） | 36 | 22% |
| 自动鉴权补齐后（报告 19） | 63 | 38% |
| 断言批量修复后（报告 20） | 72 | 44% |

> 注意：平台 `TestReport.total_count` 在 verify 重跑时会累加（164→199→312），
> 直接按报告字段算通过率会虚高（曾误报为 70%）。**统计必须用用例级口径**。

### 分诊定性率

| 报告 | 失败 | L1 定性 | 送 LLM |
|---|---:|---:|---:|
| 报告 8 | 126 | 121（96%） | 5 |
| 报告 20 | 91 | 57 → 82（加规则后） | 34 |

L1 前置过滤实测省下 63~97% 的 LLM 调用量。

### 已完成

- ✅ 2.1 自动鉴权补齐（`auth_provider` 配置组 + `_ensure_auth_vars`）
- ✅ 1.1 变量闭合校验（改为按步骤顺序累积）+ `needs_fix` 标记（方案 2：标记但不丢）
- ✅ 2.3 L1 确定性分诊（7 类规则）+ 2.5 报告页失败归因面板
- ✅ L2 = L1 作为既有 AI 诊断的前置过滤（不另起炉灶）
- ✅ 2.2 双运行模式（「运行」/「AI 自愈运行」+ 模型下拉，默认仅规则免费）
- ✅ 3.2 `fix.insert_steps`（AI 可补**用户可见**的前置步骤，白名单严格）
- ✅ P0-1b 响应约定补齐成功状态码（治本：均衡采样 + prompt 要求单独成条）

### 未做 / 待定

- ⬜ **2.4 影子验证**：现有 `apply_report_fixes` 已含"应用→重跑→绿变红回滚"，
  影子验证的增量价值只是把顺序改成"先验证再应用"。重要但不紧急。
- ⬜ **1.2 前置链模板化**：`insert_steps` 已能覆盖大部分场景，优先级下降。
- ❓ **登出幂等语义**：L2 判 `POST /api/auth/logout` 无 token 返回 200 是「接口问题」，
  但代码看像有意设计的幂等。**需产品决策**；若确为有意设计，说明 L2 prompt 缺
  「平台自身设计约定」上下文，该结论应回流 `user_feedback`。
- ⚠️ **测试套件自我污染**：L2 发现"管理员 token 已失效，疑似前序用例改了管理员密码"。
  比断言错误更深一层的结构问题，未解决。
