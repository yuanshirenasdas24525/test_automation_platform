# 硬性要求

1. **只覆盖上面列出的本批测试点**，一个测试点通常对应 1 条用例（若该点明显含正反两面，可拆 2 条）；遇到「能力边界」判定越界的点则跳过。
2. **操作步骤必须「控件级」详细**，能让没看过系统的人照着一步步操作。示例（粒度参考，非照抄）：
   - `打开被测系统登录页`
   - `在「用户名」输入框输入有效的测试账号`
   - `在「密码」输入框输入对应的正确密码`
   - `点击「登录」按钮`
   **不要硬编码环境相关的具体值**：不要写死具体 URL / 端口 / IP（用「登录页」「首页」这类页面名指代）；账号、密码、数据用需求摘要 / 前置条件里给出的值，需求没给就用占位描述（如「有效的测试账号」「对应的正确密码」），**不要臆造**具体用户名（如 test_user）。
3. **预期结果具体、可验证**，且**只写用户在页面上能观察到的结果**：提示文案、页面跳转、元素状态（置灰 / loading / 掩码）、列表或数据的可见变化。功能用例**禁止写接口层断言**——不要出现 JSONPath（如 `$.data.access_token`）、HTTP 状态码（200 / 401 / 422）、接口路径、请求/响应字段名、令牌字段（access_token / refresh_token）。接口层校验属于接口用例，不在功能用例里。
4. **前置条件**：列出必要前置（如「已存在 admin 账号」），无则空数组。
5. **连贯性（重要）**：术语、页面名、控件名要与需求摘要和已生成用例保持一致；**绝不重复「已生成用例名」里的用例**；涉及跨模块的点要在前置或步骤里写明关联。
6. `steps` / `expected` / `preconditions` 都是字符串数组，每个元素一条，**不要自己加序号前缀**（前端会自动编号）。
6.5. **category**：原样照抄该测试点的类别（正向/异常/边界/权限/跨模块/其它），只填类别词本身，不要自己往 name 里加——系统会自动拼成「【类别】用例名」。
7. **决定插入位置（after，重要）**：参考上面「本模块现有用例」的执行顺序，为每条新用例指定它应当**插在哪条现有用例之后**，写进 `after` 字段：
   - `after` = 现有某条用例的**完整名称**（从现有清单里**原样照抄**），表示新用例排在它后面；
   - 若该用例应排在所有现有用例**最前面**，`after` 写 `"__START__"`；
   - 若放到**末尾**或无明显归属，`after` 写 `""`（空字符串）；
   - 让新用例落在逻辑相邻的位置（如新增的「登录失败锁定」应紧跟现有「登录」相关用例之后），保证整体执行顺序连贯。
8. **优先级 `priority`（0/1/2/3，0 最高）**，按用例真实重要性给，**不要全填同一档**：
   - `0` 冒烟核心：主干正向流程（如登录成功并跳转）、核心权限跳转，以及"挂了整个功能就不可用"的最关键点；
   - `1` 主要：主要的异常 / 权限 / 校验分支（如密码错误提示、越权被拒、必填校验、锁定）；
   - `2` 次要：边界值、界面与交互细节（置灰 / loading / 回显）、兼容性；
   - `3` 边角：可有可无、极少触发的场景。
