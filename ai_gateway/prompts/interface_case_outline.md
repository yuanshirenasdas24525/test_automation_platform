# 要求

0. **只规划新增/补充的测试点**：上面「已有用例」覆盖到的不要再列。
1. **按覆盖力度规划，不要三档都生成同样数量**：
   - 如果覆盖力度是“标准覆盖”，只覆盖每个接口的主流程 + 最关键风险点，不要逐字段穷举。
   - 如果覆盖力度是“全面覆盖”，对每个接口和核心参数系统覆盖，适用维度都要有代表性测试点。
   - 如果覆盖力度是“穷尽覆盖”，才对每个接口、每个参数、每个维度逐项拆开，宁可多列、不要漏。
2. **测试维度池**：规划时从下面维度中按覆盖力度取舍：
   - 正常请求（合法参数 → 成功响应、正确状态码与字段）
   - **每个必填参数**各一条：缺失 / 为空
   - **每个参数**的类型或格式错误（该传数字传字符串、非法日期/邮箱/手机号格式、特殊字符）
   - **每个有范围的参数**的边界值（最小/最大/刚好/超界、0/负数、长度边界、超长）
   - 鉴权：无 token / token 失效 / token 格式错 / 过期
   - 越权：用 A 的身份访问 B 的资源、普通用户访问管理员接口
   - 响应校验：状态码、关键响应字段、错误码与错误信息
   - 幂等 / 重复提交、并发（如适用）、分页与排序的边界（页码 0/超大、size 边界，如适用）
   - 安全：SQL 注入 / XSS 特殊字符入参
   - **数据链路**：需要先调别的接口拿数据再调本接口（先登录拿 token、先建数据再查/改/删）
   - **查库校验**：接口写/改/删库时，规划「调用后用 SQL 查库校验数据正确」的测试点
2.5. **按执行顺序排列（重要）**：`points` 的先后就是将来**批量执行的顺序**。请按接口依赖排：
   - 鉴权/登录类接口在前（后续接口要用它拿到的 token）；
   - 「创建」类在「查询/更新/删除」之前（先有数据才能查改删）；
   - 同一接口：正常请求在前，参数校验/边界/异常在后；
   - 有依赖链的接口连贯成段，不要被别的接口插断（避免逻辑中断）。
3. 每个测试点用**一句话标题**概括，并标注类别（正常 / 参数校验 / 边界 / 鉴权 / 越权 / 响应校验 / 其它）。**标题要简短，只写测试意图，不要带方法和路径前缀**（如写「合法账号密码登录成功」而不是「POST /api/login 合法账号密码登录成功」）。
4. **额外产出一段「接口摘要 digest」**：把每个接口的 method、path、关键参数（名/必填/类型）、典型响应（状态码 + 关键字段）浓缩成文字，供后续分批生成详细用例复用——必须自洽、信息完整，不依赖原文档也能照着写用例。**若上面变量池里有对应变量（如账号/密码/手机号），在 digest 里注明「登录用 ${my_account}/${my_password}」之类，提示后续用例直接用变量池变量。**
5. 跨模块：接口之间有依赖（如先登录拿 token 再调其它接口、下单后查订单）要在测试点里体现。
6. 测试点数量由覆盖度决定，不要凑整；标准 < 全面 < 穷尽，三档数量必须有明显差异。
