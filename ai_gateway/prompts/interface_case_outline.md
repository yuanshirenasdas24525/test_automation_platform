# 要求

0. **只规划新增/补充的测试点**：上面「已有用例」覆盖到的不要再列。
1. **按覆盖力度规划，不要三档都生成同样数量**：
   - 如果覆盖力度是“标准覆盖”，只覆盖每个接口的主流程 + 最关键风险点，不要逐字段穷举。
   - 如果覆盖力度是“全面覆盖”，对每个接口和核心参数系统覆盖，适用维度都要有代表性测试点；**正向、逆向（参数/边界/鉴权/越权）、安全、场景、模块关联五大类都要有，缺一不可**。
   - 如果覆盖力度是“穷尽覆盖”，对每个接口、每个参数、每个维度逐项拆开，宁可多列、不要漏；安全、响应校验、数据链路、查库、场景用例都要成体系展开。**穷尽模式不要为了简洁合并测试点，应尽量多规划可执行的独立点**。
   - 若上面给了「指定维度」清单，则**只规划清单内的维度**，其它维度跳过（用户主动收窄了范围）。
1.1. **穷尽覆盖特别规则（只在覆盖力度为“穷尽覆盖”时生效）**：
   - 输出目标是“最大化测试点数量和维度完整性”，优先多拆，不要因为担心列表长而压缩。
   - 对每个接口至少规划：正常、必填缺失、为空、null、类型错误、非法字符、鉴权、越权/权限、响应校验、安全、数据一致性/查库（如适用）。
   - 对每个请求字段尽量分别拆点；同一字段的缺失、为空、null、类型错误、特殊字符不要合成一条。
   - 响应状态码、关键字段、错误码/错误信息、列表结构、分页字段、敏感字段脱敏可以拆成独立 `响应校验` 点。
   - 场景链路既要有端到端链路点，也可以把链路中的关键单接口校验拆成独立点；不要只保留一条总场景。
   - 文档未给明确 min/max 时，可以规划“探索性边界/鲁棒性”测试点（如超长字符串、空白字符、特殊字符、超大页码），但标题中不要虚构具体业务规则。
   - 并发/性能类不要写成平台无法执行的压测；可以改写成可执行的顺序重复、快速连续调用、大数据量分页、重复提交、幂等性验证等独立点。
2. **测试维度池**：规划时从下面维度中按覆盖力度取舍：
   - 正常请求（合法参数 → 成功响应、正确状态码与字段）
   - **每个必填参数**各一条：缺失 / 为空
   - **每个参数**的类型或格式错误（该传数字传字符串、非法日期/邮箱/手机号格式、特殊字符）
   - **每个有范围的参数**的边界值（最小/最大/刚好/超界、0/负数、长度边界、超长）。标准/全面模式下，临界值必须优先取自文档里的真实约束（min_length/max_length/最大最小/枚举/正则 pattern），文档没给约束就不要虚构具体规则；**穷尽模式**可以额外补“探索性边界/鲁棒性”点，但标题里只写测试意图，不要编造不存在的长度/复杂度要求。
   - ⚠️ **格式/长度/类型/特殊字符边界优先放在"会校验该字段的接口"上（通常是创建/注册/更新）**。标准/全面模式下，登录接口只覆盖必填缺失、为空、null、密码错误、账号不存在；**穷尽模式**允许为登录/认证接口额外规划类型错误、空白字符、超长输入、特殊字符、重复登录等鲁棒性点，但不要声称服务端一定有格式校验。
   - **总原则：一条负向/边界用例必须有"能让它有意义地失败"的依据**——要么服务端确实会对该输入做校验并返回特定错误，要么有对应的前置数据。否则不要规划。
   - 鉴权：无 token / token 失效 / token 格式错 / 过期
   - 越权：用 A 的身份访问 B 的资源、普通用户访问管理员接口
   - 响应校验：状态码、关键响应字段、错误码与错误信息。标准/全面模式下，不要把主流程成功响应里的字段校验单独拆成新测试点，应合并进对应「正常」用例的断言；**穷尽模式**可以把成功响应字段、错误响应结构、分页字段、敏感字段脱敏等拆成独立 `响应校验` 点。
   - 幂等 / 重复提交、分页与排序的边界（页码 0/超大、size 边界，如适用）
   - **并发/性能/压测：本平台顺序执行单请求，无法表达真并发，不要规划纯并发/性能/压测测试点**。若关心"多次登录稳定、token 各自有效"这类，改成可执行形式：**连续多次（顺序重复）调用，每次校验都成功、各自 token 非空**（用一条多步 `requests` 的场景用例表达），类别标 `场景`。
   - **安全**：SQL 注入 / XSS / 特殊字符入参、敏感字段越权读取、未授权访问（按覆盖力度至少给代表性安全点）
   - **数据链路**：需要先调别的接口拿数据再调本接口（先登录拿 token、先建数据再查/改/删）
   - **场景（端到端业务流）**：标准/全面模式下，把多个接口串成一条贴近真实业务的链路作为**一条**测试点（如「注册→登录→下单→支付→查询订单」），类别标 `场景`；**穷尽模式**既要保留端到端链路点，也可以拆出关键中间状态、失败分支、回滚/清理链路等多个场景点。
   - **模块关联**：本模块接口依赖其它模块产出（如先在「用户模块」注册/登录拿 token，再调「订单模块」），或本模块产出被其它模块消费时，规划一条体现跨模块依赖的测试点，类别标 `关联`。
   - **查库校验**：接口写/改/删库时，规划「调用后用 SQL 查库校验数据正确」的测试点
   - **前置链（按需规划，最多一条，排在最前）**：仅当**本模块用例需要登录态(token)、但被测接口本身不是登录/认证接口**时，才规划一条 `前置链` 测试点，跨模块去登录/建账号拿到 token 供本模块复用。
     - **如果本模块就是登录/认证模块**（被测接口就是 login / token / 注册），**不要再单独出前置链**——它的"正常登录成功"用例本身就会 extract 出 token 供 `/me`、`/password` 等用例复用，再来一条前置链是重复。
     - 它产出共享变量（如 `token`、`user_id`），后续用例直接 `${token}` 引用，不要每条用例都重新登录。
2.5. **按执行顺序排列（重要）**：`points` 的先后就是将来**批量执行的顺序**。请按接口依赖排：
   - **`前置链` 永远排在最前**（它产出 token，后面都依赖它）；
   - 鉴权/登录类接口在前（后续接口要用它拿到的 token）；
   - 「创建」类在「查询/更新/删除」之前（先有数据才能查改删）；
   - 同一接口：正常请求在前，参数校验/边界/异常在后；
   - 有依赖链的接口连贯成段，不要被别的接口插断（避免逻辑中断）。
3. 每个测试点用**一句话标题**概括，并标注类别。**类别只能从这组里选**：`前置链` / `正常` / `参数校验` / `边界` / `鉴权` / `越权` / `响应校验` / `安全` / `场景` / `关联` / `其它`（账号准备链标 `前置链`、安全用例必须标 `安全`、端到端业务流必须标 `场景`、跨模块依赖必须标 `关联`，不要全塞进「其它」）。**标题要简短，只写测试意图，不要带方法和路径前缀**（如写「合法账号密码登录成功」而不是「POST /api/login 合法账号密码登录成功」）。
3.1. **禁止无意义重复拆点**：标准/全面模式下，如果某条 `正常` 测试点已经是「登录成功 / 创建成功 / 查询成功」，不要再额外规划「登录成功返回 token 非空」「登录成功返回用户信息」「创建成功返回 id」这类只检查成功响应字段的 `响应校验` 点；这些字段必须写入该正常用例的 `assertion`，而不是变成独立用例。**穷尽模式**允许把关键响应字段、错误字段、列表结构、分页字段、权限字段拆成独立响应校验点，但标题必须体现不同校验目标，不能只是换一种说法重复同一件事。
4. **额外产出一段「接口摘要 digest」**：把每个接口的 method、path、关键参数（名/必填/类型/**真实约束** min_length·max_length·数值范围·枚举·pattern）、典型响应（状态码 + 关键字段）浓缩成文字，供后续分批生成详细用例复用——必须自洽、信息完整，不依赖原文档也能照着写用例。**字段的长度/范围/枚举约束务必写进 digest**（如 `new_password: string, 必填, min_length=1, max_length=128, 无复杂度要求`），后续边界用例要靠它取真实临界值；文档没写的约束就别在 digest 里编。**若上面变量池里有对应变量（如账号/密码/手机号），在 digest 里注明「登录用 ${my_account}/${my_password}」之类，提示后续用例直接用变量池变量。**
5. 跨模块：接口之间有依赖（如先登录拿 token 再调其它接口、下单后查订单）要在测试点里体现。
6. 测试点数量由覆盖度决定，不要凑整；标准 < 全面 < 穷尽，三档数量必须有明显差异。
