# 要求

0. **只规划新增/补充的测试点**：上面「已有用例」覆盖到的不要再列。
1. **逐接口覆盖**：对文档里的**每一个接口**，都要规划以下维度（按接口实际情况取舍）：
   - 正常请求（合法参数 → 成功响应、正确状态码与字段）
   - 必填参数缺失 / 参数为空
   - 参数类型或格式错误（如该传数字传了字符串、非法日期、超长）
   - 边界值（最小/最大/0/负数/超界）
   - 鉴权：无 token / token 失效 / token 格式错
   - 越权：用 A 的身份访问 B 的资源
   - 响应校验：状态码、关键响应字段、错误码与错误信息
   - 幂等 / 重复提交（如适用）、分页与排序（如适用）
2. 每个测试点用**一句话标题**概括，并标注类别（正常 / 参数校验 / 边界 / 鉴权 / 越权 / 响应校验 / 其它）。标题里尽量带上接口（如 `POST /api/login`）。
3. **额外产出一段「接口摘要 digest」**：把每个接口的 method、path、关键参数（名/必填/类型）、典型响应（状态码 + 关键字段）浓缩成文字，供后续分批生成详细用例复用——必须自洽、信息完整，不依赖原文档也能照着写用例。
4. 跨模块：接口之间有依赖（如先登录拿 token 再调其它接口、下单后查订单）要在测试点里体现。
5. 测试点数量由覆盖度决定，不要凑整。
